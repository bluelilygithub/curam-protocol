# Plans

Added 2026-11-08. A plan is a named set of **steps**, each with a length in working days and optional "waits on" links, drawn as a Gantt. Route `/plans` (the list) and `/plans/:id` (one plan). Everyday group in the navigation. Flag **`plans`**, lifecycle **`preview`**, **off by default** (admins can always open it).

**Why its own tool, and why steps are not Tasks.** "Project" used to mean a chat workspace; the owner wanted a place for dated, dependent work that came from a diagram or a note. Tasks already has a Timeline (`client/src/components/tasks/TaskTimeline.jsx`) and dependencies (`task_dependencies`), but about 100 queries across 25 server files read the `tasks` table (digest, attention list, dashboard, calendar, fitness, goals, clients). Putting plan steps in `tasks` behind a `planId` would mean touching every one, and a single missed query would flood the digest with overdue steps. So **plan steps are their own rows** (`plan_steps`) and reach Tasks only when the person sends one (see "Send to Tasks"). The Timeline is shared, not copied.

## What it does

- **A plan** has a name, notes, a start date, a "finish by" date, a working week (Monday to Friday, or every day), and a status label (draft, active, done, archived). Up to 100 per person.
- **Steps** have a name, a length in working days, an optional **pinned start**, a status (to do, in progress, done), notes and an optional parent (a **group**). Up to 300 per plan. A **milestone** has no length and shows as a diamond. A step with sub-steps is a **group**: it has no length of its own and spans its children.
- **Waits on:** a step starts the working day after the last step it waits on ends. Steps that wait on nothing start together on the plan's start date. A circle is refused (`wouldCycle`), and groups take no dependencies (link their sub-steps instead). A step that has dependencies cannot become a group, and the plus button on it is disabled.
- **Any two of start, end and length:** start + lengths gives the finish; an end date + lengths with **no** start suggests one ("Use Fri 11 Dec" button); if both are set it says whether the steps **fit**, exactly, with room (working days spare), or are **over** (by how many working days) and what to do about it. It never squeezes the lengths by itself.
- **Pinned start:** change a step's date and it is held there (a pin button un-holds it). If a step it waits on runs past that day it is marked **clashes** in the table; the date is kept, not silently moved.
- **The timeline** is the Tasks timeline fed from the plan (`showBlocked={false}`, because waiting is normal in a plan; opens at Week zoom when the plan is four weeks or shorter). Clicking a bar jumps to the step's row. **Drag a bar to move its step** (a drop pins the step's start to that day) or **drag its right edge to change its length** (the length becomes the working days from the step's start to where the edge was left, never below one). A group cannot be dragged (its dates come from its sub-steps) and a milestone can only be moved. Click without dragging jumps to the step's row. The drag logic is `dragToStepChange` / `workDaysInclusive` in `planLogic.mjs` (tested) and the pointer handling is in `TaskTimeline.jsx` behind its new `onBarChange` prop, so Tasks' own timeline is unchanged.
- **Delete:** a plan goes to the shared recycle bin whole (steps, dependencies and links, dates as text) with an Undo button, 30 days. **A single step is deleted for good** (its sub-steps and links go with it; the page asks first). Steps are not recycle-binned yet.

## Send to Tasks (added 2026-11-08)

A plan step reaches Tasks only when the person sends it. **A checklist button on every step** sends that step; **Send all to Tasks** (above the Steps table, with an inline Yes / No) sends every step not already there. `POST /api/plans/:id/send-to-tasks` with `{ all: true }` or `{ stepIds: [...] }`, in `server/services/planTasks.js`, one transaction.

- **What a task gets:** the step's title; `dueDate` = the step's **last day** (text, as Tasks stores it); `estimatedMinutes` = days x **480** (an eight-hour day, the same rule the Tasks timeline uses to draw a task's length; none for a milestone or a group); `isMilestone` for a milestone; the step's status (to do, in progress, done); priority medium; notes `From the plan "Name".` followed by the step's own notes. A step with no date yet (a plan with no start) is sent with **no due date** and the message says how many.
- **Groups:** a group becomes a parent task (no estimate; its due date is when its last sub-step ends) and its sub-steps become **subtasks** (`parentTaskId`). The button on a group sends the group and everything inside it. A sub-step sent alone becomes a top-level task unless its group is already a task, in which case it goes under it.
- **Waits-on** links between steps that now have tasks become **`task_dependencies`**, so the Tasks timeline draws them. A link is skipped if it would close a circle with dependencies already in Tasks.
- **Once only:** each task is recorded in `plan_links` (kind `task`, `refId` the task's id, `stepId`). A step whose task still exists is **skipped**, not sent twice. If the task was **deleted** (the page counts only links whose task exists, `get()` returns `tasks: { stepId: { taskId, status } }`), the step shows as not sent and can be sent again; the stale link row is replaced in the same transaction. The button then shows a tick and **opens Tasks** (`/tasks`; Tasks has no per-task link yet).
- **A copy, with one thing coming back.** Later changes to a step's dates, name or length are **not** pushed to the task, and changing or deleting the task never touches the plan, **except the status**: when a task sent from a plan is ticked, started or reopened in Tasks, its plan step takes the same status (`syncStepFromTask` in `planTasks.js`, called from the three places in `routes/tasks.js` that already carry a task's status to Contract Review obligations and Fitness sessions: the single update, the bulk update and `changeTaskStatus`). Dates, titles and estimates never flow back. This is said in every tooltip, the (i) box and the guide. Plan steps appear in Tasks, the weekly digest and the Tasks calendar view **only after** being sent; nothing else that reads `tasks` ever sees an unsent step.
- **Ownership:** another person's plan or a step from another plan is "not found" and nothing is made; every task is created with the caller's `userId`. Tested in `plans.db.test.js` ("send to Tasks").
- **Not built:** pushing later plan changes (dates, names, lengths) to tasks, sending to a chosen workspace or client, setting a step's status from the plan page back to its task, and a per-task link into Tasks.

## Rules worth knowing

- **Dates are text.** `DATE` columns are read with `::text` (`PLAN_COLS`, `STEP_COLS`) and all date maths is in UTC, so a time zone or daylight-saving change can never move a step by a day. The recycle-bin snapshot uses the same columns for the same reason.
- **A leaf step's placement:** `start = max(plan start, day after every blocker's end)`, snapped to a working day, or its pinned start when it has one. `end = start + (days - 1)` working days. **A milestone is a point in time, not work:** it lands on the day the last step it waits on ends (not the day after), so a decision or sign-off adds no day, and the step after it starts the next working day. A milestone with nothing before it sits on the plan's first day. (Changed 2026-11-08 when diagram to plan was built; before that a milestone took the next day.)
- **No start at all** means nothing is placed (said plainly, not guessed). A pinned step can supply the start.
- **The server decides.** Every edit goes to the server and the page reloads; the client never computes dates (`planLogic.mjs` only formats and reorders).

## From a diagram (added 2026-11-08)

The **Make a plan** button in Diagrams (beside To Notes; shown only when Plans is switched on for the person, admins always) turns a diagram into a plan. It uses **no AI unless Estimate lengths with AI is pressed** (see below): the diagram is read off the board in the browser (`readDiagram` in `client/src/pages/drawings/sceneDiagram.mjs`: boxes with writing, their shape, and the arrows joined to them with their labels) and sent to the server, which applies fixed rules (`server/services/planFromDiagram.js`, pure, tested).

- **Boxes** become steps of one working day unless the person gives a length. **Decisions** (diamonds) and **end ovals** become milestones; a **Start** oval with nothing before it is dropped (it is not work). An arrow means the next step waits on the one before.
- **Decisions are assumed to be Yes.** An arrow leaving a decision whose label says no (`no`, `n`, `nope`, `false`, or starting with reject, decline, deny, fail, cancel, refuse, or the word not) is left out, and so is any step reachable only through it. Unlabelled and any other label are kept. A tick in the box, **Include the No branches as steps**, brings them back. The box lists what was left out. Only arrows leaving a decision count: a box whose arrow says "no" is left alone.
- **Loops are left out and counted.** Forward arrows (by reading order) are kept first; an arrow that would close a circle is dropped (`wouldCycle`), because a plan cannot go in circles. "No, ask again" loops are the usual case.
- **The person is asked** for the start, the finish-by date, the working week and the days for each step, and a live line says whether it fits (Fits exactly, N working days spare, Over by N working days, or a suggested start when only the end date is given). The preview is a server call (`POST /api/plans/from-diagram/preview`, saves nothing) so the numbers come from the same rules as a saved plan.
- **Create plan** (`POST /api/plans/from-diagram`, one transaction) makes the plan (`sourceKind` `drawing`, `sourceId` the drawing), its steps (in reading order, notes say `After "Customer accepts?": Yes`), the dependencies, and **the first `plan_links` row** (kind `drawing`, the diagram's title as label). The diagram is checked to be the caller's first (another person's or a missing one is "not found" and nothing is made).
- **Two-way link:** `GET /api/plans/by-source?kind=drawing&id=N` lists the plans made from a diagram; the button then reads **In a plan** / **In N plans** with a list to **Go to** and **Make another plan**, the same pattern as To Notes. A later change to the diagram is not copied into a plan already made.
- **Limits:** 40 boxes and 80 arrows (the same as Draw it for me); with several separate diagrams on the board it uses the selected one, or the biggest. A diagram with fewer than two boxes joined by an arrow is refused with a plain message.
- **Where:** `server/services/planFromDiagram.js` (+ `.test.js`), `planErrors.js` (shared `PlanError`), `previewFromDiagram` / `createFromDiagram` / `listBySource` in `server/services/plans.js`, the three routes in `server/routes/plans.js` (named routes before `/:id`), `client/src/pages/drawings/PlanButton.jsx` and `MakePlanDialog.jsx`, the guide entry `make-plan` in `drawingsTools.mjs` and `server/services/drawingsTutor.js`. Tests: `node server/services/planFromDiagram.test.js` and the from-diagram section of `plans.db.test.js`.
- **Dialog** got a wider size, `2xl` (`max-w-4xl`), in `client/src/components/Dialog.jsx`.

## On the calendar (added 2026-11-08)

In the **Tasks calendar** (`/tasks`, Calendar view) a **Plan steps** button in its top bar turns on a layer. `GET /api/plans/calendar?from=&to=` (`calendarSteps` in `plans.js`, behind `requireFeature('plans')`; the button only appears when it answers) returns every **unfinished, non-group step of a draft or active plan that is not already a task**, placed on its **last day**, with the plan's name; the page mixes them into the calendar as read-only items titled `Step (Plan name)` (a diamond for a milestone). Clicking one, or its Mark done / Edit buttons, **opens the plan**; they cannot be dragged to another day. A step sent to Tasks shows as the task, so nothing appears twice; finished steps and Done or Archived plans are left out. The switch is remembered (`localStorage` `tasksShowPlanSteps`). Only the last day is shown, not the span. Files: `TasksCalendar.jsx` (the `planLayer` prop draws the button only), `TasksPage.jsx` (fetch and mixing). Test: the calendar section of `plans.db.test.js`.

## Estimate lengths with AI (added 2026-11-08)

In the Make a plan box, **Estimate lengths with AI** asks the model how many working days each step may take. `POST /api/plans/from-diagram/estimate` (`server/services/planEstimate.js`, behind the AI rate limit, usage feature `plans_estimate`, the workspace's **`standard`** model via `getModelsForUser`, never a hardcoded id). **The model sees only the step names and the plan name**: not the drawing, not the notes, nothing else in Vault. It is sent only the steps the plan will have (a No branch left out is not sent; a milestone has no length so is not sent). The step names and plan name sit inside `<plan>` tags the person cannot close, and the system prompt says to treat them as content. The answer is untrusted and re-checked (`normalizeEstimates`): only refs that were sent, whole days 1 to 60, a short plain reason, the first answer for a ref wins; nothing usable is a plain 502 and never the model's raw text. The numbers fill the Days boxes the person has **not** typed, each marked with a star whose hover text says what the AI assumed; changing a number makes it the person's own. Nothing is saved by the call. One request each press, shown in the button's tooltip. **A real model was not tried** (no key locally): `node server/services/planEstimate.test.js` uses a stand-in for the checking, the fence, refusals, usage logging and the model-id rule.

## Made for what comes next (not built)

- **`plan_links`** is a generic link table from a plan, or one of its steps, to anything else in Vault: `kind` (`task`, `note`, `drawing`, `sketch`, `client`, `event` ...) and a text `refId`. Diagram to plan writes the first rows (kind `drawing`, after checking the diagram is the caller's). Send to Tasks writes `task` rows. It is how "send a step to Tasks", "this step came from that diagram" and "show a plan on the calendar" are recorded without another table each time. **The target's owner is not checked when a link is stored**, so the first writer must check it per kind.
- `plans."sourceKind"` / `"sourceId"` say where a plan was made from (`drawing` and the drawing's id, for plans made from a diagram).

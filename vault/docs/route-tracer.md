# Route Tracer

Trace a path on a map with mouse or finger, see the distance live, save it as a named track. Own Vite app in `route-tracer/`, built into `dist/route-tracer-app/` by `scripts/buildRouteTracer.js` (part of `npm run build`, non-fatal), shown in Vault at `/route-tracer` through an iframe (`client/src/pages/RouteTracerPage.jsx`, which sets `allow="geolocation; fullscreen"` so the locate-me button works). Nav item "Route Tracer" (Content Creation, `route` icon), feature flag `routeTracer` (default on).

## Layout (the whole screen)
A header (name, place search, settings gear, help), then a **sidebar on the left** and the **map on the right** with its own buttons. On a phone the sidebar is a bottom sheet over the lower half of the map. The sidebar shows whatever you are doing, one view at a time: **Your tracks** (the list, with the Draw and Plan route buttons at the top; opening a track replaces the list with its detail and a back button), **Plan a route**, or **Draw a route** (`src/Shell.tsx`, `src/Panels.tsx`, `src/Plan.tsx`, `src/DrawPanel.tsx`, `src/App.tsx`; CSS in `src/styles.css`). The map never runs under the sidebar on a computer, so `fitBounds` only leaves room for the map buttons (`src/layout.ts`); on a phone it leaves room for the sheet.
- **Header search**: a deliberate search (Enter), results in a dropdown, the map flies to the pick. Always available.
- **Gear menu**: Units (km / miles), Distance markers on or off, Import GPX, Take the tour. **? button**: the how-it-works guide.
- **Map buttons** (right edge): zoom in and out, centre on my location, point north, and the layers button (Streets / Outdoor / Satellite).
- **Plan a route sidebar**: A and B fields that show place names (see below), the way of travelling as four icon buttons (walking, hiking, cycling, driving), A to B / Loop / Longer route, a length box for the last two, the routes as cards (A to B lists the shortest first as "Shortest", then "Option 2" and "Option 3"; "Suggested" marks the routing service's own first choice; loops are "Loop N" and longer routes "Route N", each with how far it is from the length asked for), and **Use selected route** with Reset and Cancel below it.
- **A and B fields**: **suggestions as you type** (`src/placeSearch.ts`, the `PlaceRow` component in `src/Plan.tsx`): from 3 letters, after a 300 ms pause in typing, one request to **MapTiler's geocoding** (`https://api.maptiler.com/geocoding/{query}.json?autocomplete=true&limit=5&proximity={where the map is looking}&key=...`, the same browser key as the map; CSP already allows the host), shown as a list (names cut to their first three parts, with the MapTiler and OpenStreetMap credit); arrow keys and Enter pick one, Escape closes, a newer keystroke cancels the older request and an answer that arrives late is never shown over a newer one, and the same words near the same place are answered from memory for 10 minutes. **Enter with nothing highlighted searches at once**, and if MapTiler cannot answer (blocked key, offline) falls back to Vault's own private search (`POST /api/geocode`, Nominatim); typing alone never falls back silently. Or tap the map / drag a pin and the field fills in the place name. **Privacy: this is the one place typed text leaves the browser for a third party without passing through Vault**; the header search and Garden Planner keep the private Enter-only lookup, which Nominatim's policy requires (no type-ahead). It counts against the MapTiler quota (a few requests per search, not one per letter). The name comes from a **reverse lookup** (`POST /api/geocode/reverse { lat, lng }`, `server/services/geocode.js` `reverse()`): one deliberate lookup per tap or pin drop, through the same one-a-second queue as searches, 20 a minute per user, remembered in memory only for about 15 minutes (a point on a map is as personal as an address: never written to `geocode_cache`, never logged, coordinates only in the request body), with the OpenStreetMap attribution. A park or shop by name wins, else "12 Smith St", then the suburb; if Nominatim knows nothing there (or is unreachable) the field shows the coordinates. `NOMINATIM_REVERSE_URL` overrides the endpoint (default: the search URL with `/search` swapped for `/reverse`).

## Colours and fonts (Vault's own look)
Route Tracer wears the theme and font chosen in Vault's Settings, not its own palette. Vault saves them in `localStorage['vault-settings']` (`theme`, `font`; the zustand store in `client/src/store/settingsStore.js`) and `ThemeProvider` turns them into `--color-bg/-surface/-border/-primary/-text/-muted` and a Google Font. The app is served from Vault's origin, so `src/theme.ts` reads that same key, imports the **same theme and font table** (`client/src/themes.js`, through the `@vault-client` alias), and writes the same variables (plus `--color-on-primary`, the text colour for primary buttons: white as in the rest of Vault, near-black only where white would be under 3:1, e.g. Midnight Blue) and `--font-sans`; the fonts load from Google Fonts exactly as Vault does. A theme or font added to `themes.js` shows up here with no change. It follows a change made in another tab live (`storage` event), and falls back to Vault's default (Warm Sand, DM Sans) when nothing usable is saved. **The default font, DM Sans, is linked in `index.html`**: Vault loads it in its own page, and this app runs in a frame, which does not share the fonts the page around it loaded (without the link it showed the system font); other fonts are added by `theme.ts`; a theme or font name that Vault does not offer is ignored (nothing from storage is put into the page unchecked). `src/styles.css` uses only those variables (the fallbacks are Warm Sand), with no dark-mode media query: dark comes from picking a dark theme in Vault. Status colours (errors, success) stay fixed, as everywhere in Vault; the map's own style (Streets / Outdoor / Satellite) is separate. Tests: `tests/theme.test.ts` and the "Vault's look" block in `npm run e2e`.

## Server
- `server/routes/routeTracksRouter.js` (pool injected; `npm run test:route-tracks`) mounted at `/api/route-tracks` behind `requireFeature('routeTracer')`.
- Table `route_tracks` (`server/db.js`): uuid id, `"userId"` (every query filters on it), name (1-120), notes (2000), color (`#RRGGBB`), `geometry` JSONB (GeoJSON MultiLineString, one line per stroke, `[lng, lat]`), `"distanceM"`, `"pointCount"`, `bbox`, `"drawMode"`, timestamps (millisecond precision, so the `(createdAt, id)` paging cursor is exact).
- The server recomputes distance, point count and bbox from the geometry (`server/services/routeTracerGeo.js`, haversine with turf's earth radius, so it matches the live readout) and ignores client-sent values. Refused: over 20,000 points, over 2,000 strokes, a stroke under 2 points, any coordinate outside lng ±180 / lat ±90, a body over 1 MB (413; the global JSON limit is 30 MB, so this route checks `Content-Length` itself), more than 1,000 tracks per user.
- `GET /config` returns `{ maptilerKey }` (the browser key). `GET /` lists newest first, `?q=` name search, `?limit=` (max 100), `?cursor=`. `GET /:id/gpx` returns GPX 1.1, one `<trkseg>` per stroke. `POST /delete { ids }` is the list's multi-select (max 200 ids, uuids validated, only the caller's own tracks match, answers `{ deleted }`); in the Tracks panel: tick rows, Select all, Delete (N) with an inline Yes / No. Named routes come before `/:id`.
- `/api/geocode` (place search) is shared with Garden Planner: it now sits behind `requireAnyFeature('gardenPlanner', 'routeTracer')` (`server/middleware/auth.js`).

## Map key
If `ROUTE_TRACER_MAPTILER_KEY` is unset the app falls back to `MAPTILER_API_KEY`, which then **is sent to the browser** (visible in network requests). A referrer restriction on that shared key would also block Garden Planner's server-side tile proxy (server requests send no referrer), so prefer a separate key. `ROUTE_TRACER_MAPTILER_KEY` is a **second** MapTiler key, used in the browser (MapLibre fetches style JSON, tiles, sprites and glyphs from `api.maptiler.com`, each with the key in its URL). In the MapTiler dashboard restrict it by HTTP referrer to the Vault domain and `localhost`. It is separate from `MAPTILER_API_KEY` (server side, Garden Planner satellite proxy). Production CSP allows `https://api.maptiler.com` in `connect-src` and `img-src`. For `npm run dev` inside `route-tracer/` without a server, `VITE_MAPTILER_KEY` is an optional fallback.

## Client (`route-tracer/`)
- `src/geo.ts` (distance, simplify, bbox, formatting, GPX, validation) and `src/drawing.ts` (pure drawing state: strokes, undo, continue-a-stroke) are unit tested (`npm test`). `src/useDrawing.ts` only turns pointer events into those functions.
- Freehand: Pointer Events with pointer capture, a point is kept when 4 px from the last, a press within 24 px of the last stroke's end continues that line, strokes are simplified at about 1 px on release. A second finger cancels the stroke and hands over to the map (pinch / two-finger pan); Space + drag pans with a mouse. Click mode: each click adds a vertex, rubber band, double-click finishes.
- **Edit points** (third mode in the drawing toolbar, also the track's "Edit points" button): handles on every point and a small dot in the middle of each segment (longer than 28 px on screen). Drag a point to move it, drag a dot to add a point there, tap a point then "Delete selected point" (or Delete) to remove it; a stroke keeps at least two points. A press on nothing pans the map. Each drag, add and delete is one undo step; saving PATCHes the same track. Only handles in view are drawn (max 2,500). The pure rules (`setVertex`, `insertVertex`, `deleteVertex`, `hitTest`) are in `src/drawing.ts`.
- **Distance markers** (`src/Markers.tsx`, maths in `src/geo.ts`: `markersAlong`, `thinFactor`): numbered dots every 1 km (every 1 mi when units are miles) along the drawing in progress and the open track, placed by interpolating along each segment. Distance carries on across strokes without counting the gap, so marker 5 is where the readout says 5 km. Zoomed out they thin to every 2nd / 5th / 10th ... (at least 44 px apart, at most 300). DOM markers, not a map text layer, because text layers need the style's own font names and those differ between Streets, Outdoor and Satellite. The Markers button turns them off (remembered per browser).
- **Tap a track for distance from start** (`src/Probe.tsx`, maths `nearestOnLines` in `src/geo.ts`): tap or click within 22 px of the open track (or any track when Show all is on) and a pin lands on the nearest point of the line with a readout of "X from start" and "Y to go". The foot of the perpendicular is found in screen space and mapped back along the segment; distance is along the line and carries across strokes without the gap, so it matches the readout and markers. Not active while drawing or editing (a tap already means something there). Tap away, Escape, or opening another track clears it.
- **Route shapes** (drawing toolbar, any mode, also when editing a saved track; pure functions `closeLoop` / `outAndBack` in `src/drawing.ts`, each one undo step): *Return to start* adds one straight segment from the end of the route back to its first point (refused when already within a metre of the start). *Out and back* retraces the route in reverse so the distance exactly doubles; with several strokes the last stroke carries straight back and the earlier ones follow, each reversed, so gaps between strokes stay gaps. Both refuse past the 20,000-point limit. They are buttons, not toggles: Undo takes them back, and Out and back can be applied twice. A snapped return along roads is not built (no routing service).
- **GPX import** (gear menu -> "Import GPX", `src/gpx.ts`): the file is parsed in the browser (`DOMParser`, no external entities) and nothing is uploaded until the track is saved. `<trk>/<trkseg>/<trkpt>` and `<rte>/<rtept>` become strokes (waypoints, timestamps, elevation and extensions such as heart rate are ignored); points with bad coordinates are left out and counted; repeated points (a stop) are dropped; coordinates are rounded to 6 decimals. A recording over the server's limits (20,000 points or about 900 KB of geometry) is simplified with a growing tolerance until it fits, endpoints kept, and the toast says by how much. Limits: file 15 MB, 2,000 strokes. The route opens in the drawing tools in Edit points mode (so a stray touch cannot draw on it) with its distance, markers and Undo; Finish opens the save dialog pre-filled with the file's name and notes, and the track is saved with `drawMode: 'import'`. Export then import round-trips exactly (tested).
- **Elevation and climb** (`src/elevation.ts`, `src/ElevationChart.tsx`): heights are read in the browser from MapTiler's `terrain-rgb-v2` tiles with the same browser key as the map (`https://api.maptiler.com/tiles/terrain-rgb-v2/{z}/{x}/{y}.webp`, metres = -10000 + (R*65536 + G*256 + B) * 0.1, decoded without colour management). The route is sampled about every 20 m (at most 500 samples), tiles come from the highest zoom (max 12) that needs 36 tiles or fewer, heights are bilinear between pixels, missing tiles are filled from their neighbours, then a 3-point moving average. **Climb and descent count only rises and falls over 3 m** (peak and valley detection) so terrain-model noise does not inflate them. Shown in the open track's panel and, with the Elevation button, for the drawing in progress (after a 400 ms pause); hovering or dragging across the chart puts a pin on the map with the height and distance. Feet when units are miles. Nothing is stored with the track; each view re-reads (tiles are cached for the session). It is a terrain model: bridges and tunnels read as the ground, heights are good to a few metres. Tile requests count against the MapTiler key's quota (about 5 to 40 per view); check your MapTiler plan's terms for terrain tiles.
- **Help**: the same pattern as the other planners. `src/help/tour.ts` is a 12-step Shepherd tour (gear menu -> "Take the tour", or Vault Settings -> Route Tracer Tour which opens `/route-tracer?tour=1`; key `vault_tour_route_tracer_completed`; the tour opens the drawing tools with a sample route for the drawing steps and puts the screen back afterwards). `src/InfoModal.tsx` is the "How Route Tracer works" guide (the ⓘ button; opens once on the first visit, key `route-tracer:info-seen:v1`). Every button, box and menu has a `title` (or `data-tip`), shown by planner-core's shared `TooltipHost` (`@planner-core/help/TooltipHost`); the end-to-end test fails if any visible control lacks one. **When a feature changes, update the guide, the tour and the tooltips together.**
- **Dragging points in Click mode**: a press on a point already placed moves it (the map stays still, one undo step, a tap on it adds nothing); a press anywhere else pans or adds a point as before. Freehand mode has no point handles; use Edit points for that.
- **Follow roads** (the switch in Click mode; `src/snap.ts` the model, `src/snapRouting.ts` the asking, `POST /api/route-tracks/leg` the server): with it on, each click is a waypoint and the road or path from the previous one is asked for (the way of travelling chosen with the four icons; remembered). The route is the clicked points plus one **leg** between each pair; a leg is `routed` (the road), `straight` (clicked with the switch off), `stale` (wants routing), `pending` (a request is out), `failed` (kept as a straight line, "Try again" re-asks) or `held` (an end is being dragged: straight until release). Undo snapshots include the route, so a click and its road undo together; answers are remembered for the session (and an hour on the server), so redoing the same clicks costs nothing; at most 4 requests at once; a leg is identified by the way of travelling and both clicked points, so an answer that arrives after an undo or a move is simply not used. Dragging a point (Click or Edit mode) re-routes the legs beside it on release only; Edit points on a road-following route shows only the clicked points and one dot per road (a new dot's legs wait for release too); Delete joins two legs into one; Return to start follows roads back; Out and back mirrors the legs and reuses the roads. Drawing a freehand stroke, or a plain click with the switch off on a plain line, turns it into an ordinary line. Follow roads starts from an empty drawing (it cannot be turned on over a plain line, an imported or planned route, or a saved track being extended) and Finish waits for the roads. A saved road route is an ordinary track whose geometry is the roads (thinned only if over 20,000 points). Costs one call per click against the routing allowance (24 a minute and 150 a day per person by default; repeats are cached); `ORS_API_KEY` is needed (the switch says so when it is missing). Tests: `tests/snap.test.ts`, `tests/drawsnap.test.ts`, the leg tests in `server/routes/routeTracks.test.js`, and the Follow roads block of `npm run e2e`.
- **Plan route** (directions between two points; `src/Plan.tsx` client, `server/services/routePlanner.js` + `POST /api/route-tracks/plan` server): tap a start (A) and an end (B), pick Walking / Hiking / Cycling / Driving (`foot-walking`, `foot-hiking`, `cycling-regular`, `driving-car`) and get up to three routes with distance and estimated time, drawn in three colours (the chosen one thick). Tap a line or a card to choose; the A and B pins are draggable (the routes are asked for again, the map is fitted to the routes once per plan and then left alone); Swap A and B; Reset. **Use this route** opens the chosen route in the drawing tools in Edit points mode (so it can be adjusted, its elevation read, and saved) and it is saved with `drawMode: 'route'`. Needs `ORS_API_KEY` (an OpenRouteService key, see below); without it `/config` says `routePlanning: false` and the Plan route button is greyed out with the reason.
  - Server: the browser never sees the key or calls OpenRouteService. `POST https://api.openrouteservice.org/v2/directions/{profile}/geojson` with `Authorization: <key>`, `coordinates: [[lng,lat],[lng,lat]]`, `alternative_routes {target_count 3, weight_factor 1.6, share_factor 0.6}` (alternatives need exactly two points and a route under about 100 km; farther apart, or if the service refuses alternatives with error 2004, it asks for a single route), `instructions` and `elevation` off. Plain-language errors: 2010 (no road or path near the start or the end), 2009/404 (no route), 2004 (too far), 429 (busy), 401/403 (key rejected, logged, never shown), timeouts and 5xx (try again). Answers are cached for an hour (same profile, both points within about a metre) and cache hits cost no quota. Limits (in calls to the service): 24 per user per minute, 150 per user per day, 36 per minute across everyone (the free Standard plan is about 2,000 directions a day and 40 a minute; check openrouteservice.org/plans). Points closer than 30 m or farther than 1,000 km are refused.
  - Attribution is required and shown in the Plan route sidebar: openrouteservice.org and OpenStreetMap contributors. Routes are only as good as OpenStreetMap; a missing path cannot be used.
  - **Loop of X km** (the Loop switch in the Plan route sidebar; `POST /api/route-tracks/loop { from, lengthKm, profile, round }`, 1 to 50 km, shown in the chosen units): one start point and a length, up to three circular routes that start and end there, each with `offPct` (how far its length is from the target, e.g. +4%). OpenRouteService's round trip (`options.round_trip { length, points: 5, seed }`, one coordinate) treats the length as a hint and can miss it badly, so the server asks for three loops (three seeds = three directions) in parallel, asks again with the length scaled by how far each missed for any loop more than 12% off (once), and returns them closest-to-target first, dropping duplicates (same length and same shape). **Different loops** asks for the next round of seeds. A loop costs 3 calls to the service (up to 3 more for the correction, skipped if the user's quota is short); answers are cached for an hour. The documentation and the forum disagree on whether the option is spelled `round_trip` or `round-trip`: the server tries `round_trip`, and if the service answers 400 for an unknown option it tries the other spelling once and remembers the one that worked (check the server log if loops always fail). In a cul-de-sac suburb or a place with few mapped paths, a loop can come out well off the target; the card shows by how much.
  - **Longer route** (the third switch in the Plan route sidebar; `POST /api/route-tracks/detour { from, to, profile, lengthKm?, round }`, 1 to 100 km, A and B no more than 50 km apart in a straight line): a route between the same two points of about the length typed. No routing service does this in one call, so: (1) ask for the direct route, which is the shortest there is and tells how much roads wind here (`directM / straight line`); with no length typed the answer is just that route and its length, which the card shows ("The direct route is X"); (2) refuse a target below 98% of the direct route (`TARGET_TOO_SHORT`) or over 4x it (`TARGET_TOO_LONG`), both with the direct distance so the page words them in the person's units; within 6% above the direct route, the direct route is the answer; (3) otherwise put a "via" point off to one side of the A-B line, at a distance solved from the target and the winding factor, and ask for A -> via -> B; three shapes (left at the middle, right at the middle, left at 0.3 of the way; other rounds use other positions), in parallel; (4) any shape more than 8% off is corrected once (the winding factor is re-measured from the answer, the via point moved, asked again) if the quota allows. Results come back closest-to-target first with `offPct`, duplicates (same length and shape) dropped. Cost: up to 7 calls (1 direct + 3 shapes + 3 corrections); cached for an hour. If the via points fall away from roads (the service answers 2010) the shape is dropped; if all are, the message says to try another length or move A or B. Roads that wind unevenly, or few paths on one side, can leave an option well off the target; the card shows by how much.
  - Not built: snapping a freehand line to roads.
- Autosave of the drawing to `localStorage` every 2 s with a Restore / Discard banner on next load; `beforeunload` warning while there is unsaved work. Units and map style are remembered per browser.
- **Map as PDF** (track detail -> "Map as PDF", `src/ExportPdf.tsx`, `src/mapCapture.ts`, `src/mapPdf.ts`; `pdf-lib`, loaded only when the dialog is used). One A4 page, landscape or portrait by the route's shape (`chooseOrientation`). The map PICTURE comes from a second, hidden MapLibre map fitted to the route's bounds at the exact size of its place on the page (CSS px = pt x 1.4, rendered at pixel ratio 2, JPEG), in the style currently selected; the on-screen map never moves. Everything on top of the picture is vector, drawn by `mapPdf.ts` with `makeProjector` (the same web-mercator maths as MapLibre for a north-up map: the e2e compares it with `map.project` to 0.01 px): the route with a white edge, distance markers (thinned to at most 40), A and B (one marker for a loop), scale bar (`niceScale`), north arrow, MapTiler and OpenStreetMap credit, the numbers (distance, climb, descent, lowest, highest), the notes (wrapped, cut with "..."), and the elevation profile (same `buildProfile` as the chart; if it fails the PDF is still made and says "Heights not included"). Text goes through `safeText` because the standard PDF font only has Latin characters (anything else prints as "?"). Title, notes and profile are all length-bounded. `mapPdf.ts` never touches the DOM and is unit tested; `captureMap` waits for the tiles (30 s limit, plain message, a 401/403 from MapTiler is reported as such).
- **Email the PDF**: `POST /api/route-tracks/email { to, subject, message, copyToMe, filename, pdf }` (base64) sends through Vault's shared `server/utils/sendEmail.js` (MailChannels key or SMTP, the same as invoices), as an attachment. The server is the only thing that decides what is sent: signed-in users only (the router is behind `requireFeature('routeTracer')`); exactly ONE recipient that passes a strict address check (no commas, semicolons, angle brackets, spaces or newlines, so no extra recipients or header injection); the attachment must decode, start with `%PDF-` and be under 8 MB (body under 12 MB, answered 413); the message is plain text, at most 2,000 characters, HTML-escaped; subject and file name are cleaned; the sender is added as Reply-To (never as From, which stays the workspace address); "copy to me" goes to the user's own account address only and not at all if it equals the recipient. Per-person allowance of 10 an hour and 30 a day (429 with Retry-After; a failed send does not use any). The log records the size only, never the address or the words. A provider error is logged and answered as a plain "could not be sent" (provider text can contain keys); "not configured" is a 503 "Email is not set up on this server yet", and `GET /config` returns `emailEnabled` so the dialog can switch the form off and say why. Needs `MAIL_CHANNEL_API_KEY` or `SMTP_HOST`/`SMTP_USER`/`SMTP_PASS` (already used by Finance), and respects `DISABLE_EMAIL`. Tested in `server/routes/routeTracks.test.js` (`/email`, `/config`) and the browser e2e.
- GPX is fetched with the auth header and saved from a Blob link (a plain link or `window.open` would be unauthenticated and, in the iframe, unreliable).
- `npm run e2e` (needs `npm run dev` running, Chrome installed) draws, undoes, pans, zooms, saves, reloads, extends, deletes and tries touch, with MapTiler and the API stubbed in the browser.

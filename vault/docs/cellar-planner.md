# Cellar Planner

Walk-in wine cellar configurator. **Glass enclosure with metal racking first**, then carcass joinery. Bespoke-first: everything is driven by dimensions in whole millimetres, not product codes. Code: `vault/cellar-planner/` (own Vite app on `planner-core`). Full specification and decisions log: `cellar-planner/specs/spec-v1.md` (v1.1).

> **Status: in Vault, switched off by default.** The page is at **`/cellar-planner`** (an iframe hosting the built app at `/cellar-planner-app/`, the same pattern as Garden Planner), with a nav item **Cellar Planner** (Content Creation), a Settings → **Cellar Planner Tour** card, and the feature flag **`cellarPlanner`**. The flag **defaults to off** (it is a work in progress with unverified values): an admin switches it on in **Settings → Feature Access**, which shows the nav item. The `/cellar-planner` page itself does not depend on the flag (as for the other planners), so the address works for any signed-in user. Designs save to the Vault account through `/api/cellar-projects` (table `cellar_projects`, behind `requireFeature('cellarPlanner')`), with a `.cellar.json` file download and a browser draft as fallbacks. It is built by the root `npm run build` (`scripts/buildCellarPlanner.js`, non-fatal: if it fails Vault still deploys and the page shows a "not available in this build" notice). It can also run alone with `npm run dev` inside `cellar-planner/` (port 5176, `http://127.0.0.1:5176/cellar-planner-app/`, trailing slash included).

## Using it

- **The first visit opens the Test case**, so there is never an empty screen. After that the saved draft comes back (so a browser that already has a blank draft keeps it until you press **Test case**). **Test case** (button, `?testcase=1`, or open `examples/test-case-1.cellar.json`) loads the sample enclosure with racks on every wall (4 units north, 1 either side of the door on the south, 1 each on east and west) filled with **best-guess rack values**: a 600 x 350 mm unit, 2000 mm tall, 100 mm row pitch, 7 neck-out bottles a row, 2 posts, **1,120 bottles**. **These are invented, not a supplier's.** Each is marked **estimated** (a visible word, not just colour) with a banner saying not to quote from them; typing your own number over one, even the same number, removes its marker, and undo brings it back. The minimum walkway stays blank. `npm run example` rewrites the example file from the app's own test case, and a test fails if they differ.
- **Blank sample** (the old "Sample" button) loads the Carter Noir sample enclosure **as read**, with the racks left blank, and the amber "not set" banner has a **Fill the blanks with best guesses** button that fills only the blank rack fields (keeping anything you typed, marking just those estimated; Undo takes them back). The sample is the Carter Noir enclosure **as read** from sheets A101 to A103 (2850 x 1665 x 2200 mm, 50 mm panels, a 970 x 2120 door centred on the south wall hinged on the left, a 500 mm header with a conditioner and two vents). **Every number from the sample is unverified.**
- **Enclosure panel:** outer sizes (to the outer faces), ceiling and floor build-up, header height. **Walls:** each wall's kind (insulated panel, framed glass, stud wall) and build-up; the build-ups are taken off to give the **inside size** (sample: 2750 x 1565 x 2150). **Door:** wall, size, swing, hinge as seen from outside, offset (blank = centred), glazed. **Header:** conditioner and vents, positioned from the header's left end.
- **Rack specification:** unit width, depth, height; row pitch; bottles per row; orientation; posts; optional rows. **All start blank.** **Minimum walkway:** blank until you set it.
- **Rack runs:** add a run on a wall, or **Fill** a wall with whole units (leaving the door opening free).
- **Plan** (from above), **Elevation** (any wall, seen from outside) and **Racks** (the inside face of any wall, seen from inside, with **every bottle drawn at its true size and spacing**: end-on circles for neck-out racks, side-on rectangles for label-forward; rows are one row pitch apart standing on the floor; the door's opening is shown on its wall; units still missing values are an outline only, never filled with guessed bottles; runs with an error are red and say "not counted", matching the total). Scroll to zoom, drag to pan, **Fit**.
- **Drawing package** (button): fill in the title block (company, client, address, project number, drawn by, checked by, date) and **Download PDF**: A3 landscape sheets, **A100** specification and schedule, **A101** plan, **A102** door-wall elevation, **A103 onward** the racks on each wall with every bottle at true size, each with the title block and the red "preliminary design only" line, and a status line saying whether the rack values are best guesses, not set or entered. The details are kept with the design. A design with no racks makes three sheets.
- **Checks** (errors, then warnings, then information, each with a fix) and **Advisory guidance** are on the right.
- **Saved designs** (`src/app/designs.ts`, `designLibrary.ts`, `ui/DesignsPanel.tsx`): designs save by themselves, 1.5 s after the last change, to **the Vault account** (table `cellar_projects`, `/api/cellar-projects`, behind the `cellarPlanner` flag) when the planner is opened from Vault while signed in, otherwise to **this browser** (and the header says which: "Saved to your Vault account ✓" or "Saved on this device only ✓"; **Save now** saves at once). It is the same library machinery as Room and Garden Planner (`planner-core/library`: `ProjectsController`, optimistic `expectedUpdatedAt` save, a 409 pauses saving and the header offers **Keep mine / Use the saved one**, unsaved changes from a closed tab are restored, and an unreachable Vault falls back to the browser with a note). **Your designs** lists them (name, rack runs, units, "best-guess values", saved time) with New design, Open file, Copy and Delete (inline Yes / No). The first design of a new library is the Test case; New design is the blank sample. **Test case, Blank sample and Open file ADD a design and open it; they never overwrite the open one.** A draft an older version kept in the browser becomes the first saved design (and is carried to an empty account once). Limits: 200 designs per user, 2 MB each. The browser draft is still kept on every change. **Download file / Upload file** (a `.cellar.json`) still move a design in and out as a file. Undo and redo cover every edit except typing the name (no undo step, so it saves quietly).

### The rules that matter

- **The total only counts runs that can be built (D-18).** A run with an error (too tall for the inside, too shallow for the bottle, off the end of its wall, in the door's way, a bottle that cannot fit) is left out of the headline number; the panel says "Not counted: n bottles in m runs with errors" and the plan labels that run "not counted (has an error)". Warnings and notes do not remove a run. Example: Test case, Magnum bottle: headline 0, 640 bottles not counted in 5 runs.
- **Bottles per row is calculated unless typed (D-19).** Blank, it is the unit width divided by the bottle's slot pitch (600 mm: Bordeaux 7, Burgundy 6, Champagne 5, Magnum 4), shown as "calculated" with a note that it is an estimate; a typed number is the fabricator's and wins. So the **Bottle** setting moves the count. A typed number that cannot fit across the unit (9 Bordeaux need 684 mm; a 600 mm unit holds 7) is `RACK_ROW_TOO_WIDE`. The Test case leaves it calculated.
- **Label-forward has its own bottles-per-row (D-20),** never calculated and "not set" until typed: the neck-out figure never carries over, because on a metal rack label-forward may mean the bottle lies side-on and takes about its own length of width.
- **Blank is "not set", never zero.** A blank rack field is shown as "not set"; a run with a blank unit width or depth has no footprint and is skipped by the geometry; the bottle total reads "not set (n runs without rack values)" until every run is complete; `RACK_SPEC_MISSING` names the missing values. There are no invented rack defaults.
- **The walkway minimum has no default and is only ever a warning.** Blank = not checked (one information note says so). A step-in glass cabinet and a walk-in room are designed to different minimums (D-17).
- **The floor-inside-the-door check applies only when the door swings in.** An inward door also gets the swing sweep tested as a true quarter circle.
- **Advisory guidance never blocks a design.** Insulation, glass (about 1.4 W/m2K or better, thermal breaks, sealed doors) and heat-source notes from the Kings Winehaus guide are information only and always begin *"Advisory only: requires mechanical engineer / HVAC sign-off."* The glass share (and the advisory 50% note that uses it) is measured on the **outer faces** (10.35% for the sample).
- **Every drawing carries** `PRELIMINARY DESIGN ONLY: FINAL SITE MEASURE REQUIRED PRIOR TO FABRICATION`.
- **The header is a bulkhead above the enclosure**, not space inside it, so it never reduces the inside height.
- **Label-forward depth is a joinery assumption on metal racks** (inclined footprint plus a 20 mm lip) until the fabricator confirms how their rods hold the bottle.

## Help: guide, tour, tooltips

Same pattern as Room Planner and Garden Planner.

- **How this works** (`src/ui/InfoModal.tsx`, the **(i)** button): the plain-language guide. **Opens once on the first visit** (localStorage `cellar-planner:info-seen:v1`), then from the button. Covers what it is, getting started, the two drawings, racks and what "not set" means, checks and advice, saving, and what is not built yet.
- **Guided tour** (`src/help/cellarTour.ts`, the **compass** button): 13 Shepherd.js steps (the same library and look as Vault's tours), loaded on first use so it stays out of the main bundle. The tour is data (`TOUR_STEPS`), tested against the `data-tour` hooks on the screen so it cannot drift away from it. The elevation step switches to the elevation and the drawing step back to the plan; the screen is put back when the tour ends. Completing or skipping sets **`vault_tour_cellar_planner_completed`** (the key Vault's other tours use, so Settings can show "Retake Tour"), and **`?tour=1`** starts it (how Vault's Settings page will retake it).
- **Tooltips:** the shared themed tooltip (`@planner-core/help/TooltipHost`, the same look as Vault's). Every button, field, menu and tab has a plain-language `title` or `hint`, written as real sentences; a test fails if one is missing. Cards are capped at 160 px wide: the shared placement keeps a card's centre 80 px from the window edge, so a wider card runs off the screen beside the left panel. (This is a latent limit in `planner-core/src/help/tooltipLogic.ts`, which assumes 240 px cards; it was not changed here because it is shared with the other planners.)

## The Racks view: the count in words, and how accurate the picture is

The Racks view (and lite's "Racks on a wall") lists the wall's bottles in a sentence under the drawing, for example "North wall: 560 bottles in 4 units (140 a unit: 20 rows of 7)." (`rackWallSummary()` in `src/views/rackView.ts`). It says "no racks" for an empty wall, names units with an error as **not counted** (with their bottles) and units with values missing as having **no bottles counted**.

**What the picture does and does not show.** One circle (or side-on rectangle for label-forward) is drawn for every bottle the count includes, no more and no fewer: a test checks that the circles on every wall equal the words and add up to the total, for the Test case and for every bottle style, door wall and door type the lite tool can make. Bottle circles are the bottle's true diameter. What is **modelled, not measured**: bottles are spread evenly across each unit's width (the real pin spacing is the fabricator's), rows are one row pitch apart from the floor (the first row's offset is not modelled), and each circle is one bottle lying front to back, one deep (racks that hold bottles two deep, or double-sided racks, are not modelled and would hold more). Rack sizes are best guesses until the fabricator supplies real ones, so the count is an estimate even though the picture matches it exactly.

## Single and double doors

Added 2026-10-09. `DoorSpec.leaves` is `1` (a single leaf, also when absent, so every earlier file and design opens unchanged) or `2`.

- **Double door:** two equal leaves that together fill `widthMm` (the whole opening), each hinged at an outer edge and meeting in the middle. The `hinge` setting is not used for a double door (the panel hides it). Each leaf sweeps a quarter circle of **half the opening** (`doorLeafWidthMm`), so a 1500 mm double door sweeps two 750 mm arcs, not one 1500 mm arc.
- **Where it shows:** the Door panel's **Door type** (switching to double sets the opening to at least 1500 mm, back to single to at most 970 mm; one undo step), the plan (an arc per leaf, `doorLeaves()` in `placement.ts`), the elevation (labelled DOUBLE DOOR, a diagonal on each leaf and the meeting line), the inward-swing and keep-clear checks (a rack is flagged if it meets either leaf's arc), the drawing package's door row, and the guide and tour text.
- **Check:** `DOUBLE_DOOR_TOO_NARROW` (error) when the opening is under 800 mm (leaves under 400 mm). `DOOR_TOO_WIDE` applies to the whole opening.
- **Not modelled yet:** a double door with one fixed leaf (only one opening), and different leaf widths. The 1500 mm default is a typical figure to confirm, like the 970 mm single door.
- **Lite tool:** a **Door type** question (single, about 970 mm, or double, about 1500 mm), in the design code as an eighth value (codes with seven values, made before this, open as single doors), in the enquiry summary line, the guide and the tour. The opening shrinks to fit a short door wall (an even number of mm for a double door).
- **Tests:** `tests/doubledoor.test.ts` (geometry, checks, drawings, saving), `tests/lite.test.ts`, and the door checks in `scripts/e2e.mjs` and `scripts/e2e-lite.mjs`.

## Lite version for the public website

Started 2026-10-09. A "play" tool for visitors: a static bundle (no Vault login, no API calls, nothing stored) embedded by iframe in the WordPress site on SiteGround. Every figure says **estimate only, not a quote**.

**What the visitor does:** types the inside width, depth and height, picks the door wall and the main bottle style, and chooses "as many as fit" or "a number I choose". They see a bottle estimate, a plan from above and the racks on any wall (pinch-zoom works), and can press **Request a quote**, which hands their design to the site's enquiry form.

**Standard rack units:** every lite estimate is built from one standard-size rack unit (`LITE_UNIT_WIDTH_MM`, 600 mm wide, a typical size not a confirmed supplier value), placed whole, so leftover space at the end of a wall shows as a gap. This is stated on the screen under the drawing, in the guide ("Standard rack units"), in the tour's estimate and drawings steps, and in the enquiry summary line. Keep those in step if the unit size changes.

**Code** (`cellar-planner/`):
- `src/lite/settings.ts` is the pure core: `LiteSettings` (clamped to `LIMITS`), `liteToProject()` (the Carter Noir sample resized to the inside size, best-guess racks marked estimated, north and south own the corners, east and west fit between; deep enough for the chosen bottle, so a magnum gets a deeper unit), `trimToTarget()` (removes whole units, east then west then south then north, never adds), `liteResult()` (estimate, the room's maximum, plain problems) and the **design code**.
- `src/lite/LiteApp.tsx` + `lite.css` is the screen; `lite.html` is its page, `vite.lite.config.ts` its build.
- `lite-wordpress/cellar-lite-fill.js` is the small script for the WordPress page.
- Reused as they are: `src/enclosure`, `src/rack`, `src/placement`, `src/views`, `src/ui/DrawingView.tsx`.

**Help for a casual visitor** (written in plain words, no planning jargon):
- **Guide** (`src/lite/LiteHelp.tsx`, the **Help** button): what the tool is, each question in plain words (how to measure the inside, what South/North/East/West mean on the drawing, what the four bottle styles are), what the two drawings show, what asking for a quote does and sends, and that figures are estimates. **Opens only from the Help button** (it used to pop up on a first visit; most visitors closed it unread, so a three-step strip on the page replaced that); Esc closes it.
- **Tour** (`src/lite/liteTour.ts`, the **Take the tour** button, or `?tour=1` on the address): nine Shepherd steps in the order the screen asks things: size, door, bottle, how many, the estimate, the drawings, the quote button. Loaded on first use so it stays out of the first download. Finishing sets `cellar-lite:tour-done:v1`.
- **Always-visible hints:** a one-line explanation sits under every question (no hover needed, unlike the full planner). All wording is in those three files, plus the field labels in `LiteApp.tsx`, for the owner's wording review.

**Design code:** `CL1.` plus base64url of `[width, depth, height, doorWall, bottle, mode, target]`. Settings only, no personal data. A link `lite.html?d=CL1....` reopens the design; the address is kept up to date as the visitor edits. Unreadable, newer-version or out-of-range codes are refused or clamped, never trusted.

**Hand-off to the enquiry form:** the embedded page posts `{ type: 'cellar-lite:design', version: 1, code, summary, bottles, requested }` to the page around it, addressed to the origin of `document.referrer` (never broadcast; nothing is posted when not embedded). The WordPress script accepts a message only from the planner's own origin, checks the code's shape and the summary length, and, once when **Request a quote** is pressed, takes the visitor to the contact page (`CONTACT_URL`) with the design in the address (`?cellar-design=` and `?cellar-summary=`). The same script on the contact page writes the summary, code and a "View this design again" link (`PLANNER_LINK` + `?d=<code>`, which reopens the design in the standalone planner) into the form's message box as one marked block, scrolls to the form, focuses its first field and removes the design from the address. The script must be loaded on BOTH pages; it logs each step to the Console while `DEBUG` is true. The revealed panel is always scrolled into view in the planner, and is the fallback (**Copy my design**) if nothing happens. The visitor still presses the form's own Send. Without the script, the quote step shows the summary and code with a **Copy my design** button to paste into the form. **No server of ours is involved**: the enquiry goes through the site's own form and email.

**Staff side (full planner):** **From design code** (title bar, Examples group) takes a pasted code, a "Design code: ..." line or a whole enquiry email, and **adds** the design as a new one (never overwrites). `?d=CL1....` on the full planner's address does the same on load. The result is the same enclosure, runs and bottle total the visitor saw (a unit test covers lite settings -> code -> project -> saved file -> reopened).

**Settings the owner controls (Vault: Settings -> Cellar Planner, admin only):** the rack types (see **Shared rack catalogue** below; the public tool uses the default one's width and height), single and double door widths, a guide-price formula, the line under the heading, and the starting rooms. Stored as one JSON value in `workspace_settings` (key `cellar_lite_config`); the rules for a valid value are in `server/config/cellarLiteConfig.js` (the admin screen shows the plain-language reason when a value is refused). The public tool is static files on the business's website, so it **fetches** them when it opens from `GET /api/cellar-lite/config` (no login, read-only, `Access-Control-Allow-Origin: *`, cached 30 s server side and 60 s in the browser; Vault must be deployed for this to work). If that request fails for any reason the tool uses the last settings it remembered in that browser, else its built-in defaults (`src/lite/config.ts`, kept equal to the server's by a test), and the browser Console says which and why (`[cellar-lite] ...`). Prices are only sent while "Showing to visitors" is on, so unpublished amounts never leave Vault. Guide price = fixed + per rack unit x number of whole units + the door price, shown as a range (+/- %) rounded to the chosen step; nothing is shown unless at least one amount is entered. A rack unit is never taller than the room. Starting rooms replace only the size and door style. **Copy a link to this design** copies the standalone planner's address with `?d=<code>`. Beside it, **How is this price worked out?** (only while a guide price is showing) opens a modal (`src/lite/PriceHelp.tsx`) that outlines how the price follows from the visitor's own choices: it names the parts in use (racking, door, the basics every cellar needs; a part is mentioned only if the owner set an amount for it) and shows how many rack units and which door THIS design has, but never any amount. Every control in the planner carries a `title` and the shared `TooltipHost` shows it as the themed tooltip; every field and button on the admin tab uses Vault's `Tooltip`. Tests: `npm run test:cellar-lite-config` (server), `npm test` in `cellar-planner/` (`tests/liteConfig.test.ts`, incl. the browser/server agreement check).

**Shared rack catalogue and staff price (Settings -> Cellar Planner -> Rack types).** The owner keeps a **catalogue of rack types** (up to 8: name, unit width/height/depth, row pitch, orientation, posts, bottles per row, bottles per row label-forward, rows per unit, **price per unit**, and a **Confirmed by supplier** tick), one marked the **default**. Blank = "not set", never zero. It is the single source for both tools: the public lite tool reads the default type (served as `rack` and `pricing.perUnit`, the same shape as before, so pages with an older copy keep working; settings saved before types existed become one "Standard rack"), and the **staff Cellar Planner** reads the whole catalogue plus the real prices from the signed-in `GET /api/cellar-planner/catalogue` (behind `requireAuth` + `requireFeature('cellarPlanner')`, `Cache-Control: no-store`; `staffView()` in `server/config/cellarLiteConfig.js`). While the public price is hidden, `publicView()` blanks every type's price too. Staff side (`cellar-planner/src/app/catalogue.ts`): the **Rack type** picker in Rack specification copies a type's numbers into the design (the design stays self-contained, so a later catalogue change never alters it; if the values then differ from the catalogue a note offers "Use the catalogue's values again"); a **confirmed** type marks nothing estimated, an **unconfirmed** one marks every value it has estimated (blanks stay "not set") and the drawing package says "NOT YET CONFIRMED BY THE SUPPLIER". New blank designs start with the default type. The **Price** panel is the full breakdown (fixed amount + units x the type's price + single/double door price, and the range a customer would see); it shows even when the public price is off, warns for unconfirmed types, a type with no price or a design with errors, and says why when there is no price (no catalogue, no type chosen, type removed, no racks, no amounts). The catalogue is remembered in the browser for offline use; without a Vault sign-in the planner still works, with a note instead of the picker. Tests: `node server/routes/cellarLiteConfig.test.js` (rules, legacy migration, public vs staff views), `tests/catalogue.test.ts` + `tests/liteConfig.test.ts` (browser and server rules must agree), `npm run e2e:catalogue` inside `cellar-planner/` (real Chrome, Vault's endpoints stood in for at the network layer, incl. accessibility scans).

**Enquiries (website contact form to CRM) and the customer quote.** *Enquiry copy.* The site's contact page keeps working as before (its own email). `lite-wordpress/cellar-lite-fill.js` (already on the contact page) now ALSO posts a copy of the enquiry when the form is submitted with a planner design in the message: name, email, phone, the visitor's own words, the design code/summary/bottles/guide price, as `text/plain` (no preflight; a keepalive `fetch` with no cookies) to the public `POST /api/cellar-lite/enquiry` (`server/routes/cellarLeadsRouter.js`, mounted before `requireAuth`, CORS `*`). It is skipped when there is no design, no name or no valid email (field selectors `NAME_FIELD`/`EMAIL_FIELD`/`PHONE_FIELD` at the top of the script; set `COPY_TO_VAULT=false` to switch it off; DEBUG lines say `copy to Vault: ...`). If Vault is down nothing is lost: the form's own email still goes. Vault validates (plain-language 400s), then in one transaction records a `cellar_leads` row and puts the person in the CRM of the **first admin**: a **prospect** client with a primary contact (or the existing client with the same email) and a **lead-stage deal** whose note carries the design summary, their message and a link `/cellar-planner?lead=ID`, plus a CRM timeline note. Guards: a hidden `website` field (answered "ok", nothing stored), 5 per visitor per hour (hashed forwarded address), 100 new enquiries per day (then 429 and a Suggestions-inbox alert), the same email+design within 24 h is one enquiry. The response is only `{ok:true}`. *Staff side.* Behind `requireAuth` + `requireFeature('cellarPlanner')` at `/api/cellar-planner/leads` (own enquiries only): list, read one (includes the design code), `POST /:id/opened`, `POST /:id/quote`. The staff planner's **Enquiries** button (count of new ones) lists them; **Open** adds the visitor's design as a NEW design (their room, door and racks), the catalogue's default rack type applied, named `Enquiry: <name>`, linked to the enquiry (`project.lead`); `?lead=ID` (what the CRM link carries; `CellarPlannerPage.jsx` passes it into the frame) does the same on load. *Quote.* **Quote** in the toolbar makes an A4 PDF (`export/quote.ts` content + layout, `quotePdf.ts` drawing, pdf-lib loaded on demand): business name/address/ABN lines, reference (`Q<date>[-E<enquiry>]`), date, valid-until, the customer, the cellar, the price lines and total from the Price panel, GST note, staff notes, the owner's terms and a fixed site-measure statement. The owner enters the business name, address lines, terms, validity days and GST note in Settings -> Cellar Planner -> **Quote details** (`quote` block of the settings; staff-only, never in the public answer). **A quote is refused** (reasons listed in the form) unless: the catalogue loaded; the design uses a rack type from it that the catalogue says is **confirmed by the supplier**; the design's rack values still equal that type's; nothing is marked estimated; racks are placed with no errors and a bottle count; a price exists; and the business name is set. Making a quote for an enquiry design logs it on the enquiry (status quoted, CRM timeline note, and the deal value is filled in only if it was empty); the PDF is made either way. Tests: `npm run test:cellar-leads` (server: validation, CRM creation, existing client, spam guards, rollback, ownership), `cellar-planner/tests/quote.test.ts` + `catalogue.test.ts` + `liteConfig.test.ts`, `node scripts/e2e-lite-contact.mjs` (the copy step in Chrome) and `npm run e2e:quote` inside `cellar-planner/` (enquiries, opening, `?lead=`, the quote, with accessibility scans). Staging checks: send the real contact form once with a design and see the client, deal and note in the CRM; open the link from the deal; make a quote. Known limits: the copy depends on the contact form firing a normal `submit` event and on its field ids; leads are owned by the first admin account, so only that account sees them in the planner list.

**Help for technicians: "How the numbers are calculated"** (calculator button in the staff planner's header, next to the (i) button; `src/help/calcExplain.ts` + `ui/CalcModal.tsx`). It works through the OPEN design with its own numbers, one table per topic (formula, working, result): inside size, the door split and opening, glass share, rack capacity (rows, bottles per row typed vs calculated vs label-forward, per run and total, what is left out), the depth a bottle needs, run footprints and what each check means, the price (lines, total, customer range) and when values count as estimated/confirmed and a quote is allowed. **Copy as text** pastes it into a ticket or an email to the fabricator. The text is built from the planner's own functions and each step carries the number it reaches (`value`); `tests/calcExplain.test.ts` runs nine very different designs (blank, label-forward, double offset door, glass, errors, supplier rows, catalogue types) and fails if any explained result differs from the engine, so the help cannot drift. When you change a formula or a default (bottle slot pitches, depth clearance, label-forward angle and lip), the test says which line of the explanation to update. Browser test: the help block of `npm run e2e:catalogue`.

**Layout of the public tool (current):** a **three-step** planner (`LiteApp.tsx`, `controls.tsx`): **1 Space** (quick-start rooms, sizes with minus/plus and metres/feet/mm, the door), **2 Racking & finishes** (bottle style, how many with a slider, rack finish oak/walnut/black), **3 Review** (summary, download PDF, price help). Every step says **Step n of 3** and its button names where it leads ("Next: Racking & finishes", "Next: Review", "Request a quote - Final step"); the step strip is clickable; moving step puts focus on the step heading. Beside the panel is a large picture (3D / Plan / Racks) with zoom + / - / reset and the sizes marked on the 3D view; along the bottom a summary bar (capacity, footprint, configuration, guide price, quote button, call link). On a phone the picture comes first, then the panel. **The door** is one drawing (`DoorPicker.tsx`): the room from above in its real proportions, walls labelled and tappable (the whole zone including the label), the door drawn as an opening with its outward swing at the chosen position and width (single narrower than double), a sentence saying what is selected, then segmented **Left / Centre / Right** (as seen standing outside) and **Single / Double**. Door position and finish are 9th and 10th values in the design code, left off while standard so old codes and links are unchanged. The **brand colour** (Settings -> Cellar Planner, default olive `#4a5a2a`, must give 4.5:1 contrast with white text) sets `--primary` and its shades.

**Visitor experience (public lite tool):**
- **Pictures:** three tabs. **Inside view** (default, `src/lite/cellarScene.ts` pure geometry + `CellarView.tsx`): a pinhole-camera picture from above the door, near wall cut away, racks full of bottles; drag to look +/-40 degrees (dragging right slides the scene right); the plan's axes are left-handed so the camera uses `up x forward` for "right" (a test guards the mirror bug). Racks against the door wall are seen from behind. **Plan from above** and **Racks on a wall** use the warm drawing look (`DrawingView look="warm" | "warmWall"`; the staff app keeps `plain`).
- **Sizes** in metres (default), feet and inches, or millimetres (`units.ts`; the design always stores whole millimetres, so design codes are unchanged); a unit written out ("275cm", "9' 6\"") wins over the selected unit; the choice is remembered in the browser.
- **Low ceilings:** the room height range is 1.8 to 3.2 m; the door is made 80 mm lower than the ceiling when the room is lower than the sample's 2120 mm door (so nothing the visitor can reach is unbuildable). `fixes.ts` is a safety net that would offer a one-click fix if a design ever could not be built.
- **Starting point:** a three-step strip replaces the old first-visit pop-up (the guide opens only from **Help**); starting-room buttons; the last design is remembered ("Welcome back", **Start again**; the untouched standard design is never remembered); a bottle slider in "A number I choose" mode; **Download my plan (PDF)** (the staff drawing package, lazily loaded `planPdf.ts`); the owner's reassurance line after **Request a quote** (`quoteNote`).
- **Door wall by picture** (`DoorPicker.tsx`): a small outline of the room in its real proportions with a button on each wall (radio group, 44 px targets, keyboard works); it stays in step with the "Door on the" menu below it.
- **Call button:** the owner's phone number (Settings -> Cellar Planner -> Phone number, 6 to 15 digits, blank = no button) shows as **Prefer to talk? Call ...**, a `tel:` link built by `telHref()` (digits and a leading +). Counted as the `call` event.
- **Pinned preview on phones:** the planner is in an auto-height frame, so nothing inside it can stick to the screen; the page script does it. The planner draws a small JPEG of the Inside view off screen (`thumbnail.ts`, 180x112, about 5 to 10 KB, redrawn 350 ms after the design stops changing, only when embedded) and sends it in the design message; it also reports where the big picture sits in the frame (`pictureTop`/`pictureBottom` on the height message). The phone bar then shows the little picture only while the big one is off screen. The script accepts only a `data:image/jpeg;base64,` string under 40 KB.
- **Page script (`lite-wordpress/cellar-lite-fill.js`, on the planner page and the contact page):** goes to the contact page when the quote button is pressed; sizes the frame to the planner (`cellar-lite:height`); on phone widths shows a fixed bottom bar (bottles, guide price, **Request a quote**) while the planner is on screen (a bar inside the frame cannot stick to the screen); passes anonymous usage events (`cellar-lite:event`: start, preset, unit, view, quote, link_copied, plan_downloaded, price_help, fix, welcome_back, call, door_pick; names and a few short labels only, never the design) to `window.dataLayer` as `cellar_lite_<name>`. Switches `AUTO_HEIGHT`, `STICKY_BAR`, `TRACK_EVENTS` at the top of the file.
- **Tests:** `npm test` (incl. `liteUnits`, `liteFixes`, `cellarScene`, `liteConfig`), `npm run e2e:lite-site` (needs `npm run build:lite` and Chrome: whole-page behaviour, owner settings, contact flow) and `node scripts/e2e-lite.mjs` (needs `npm run dev:lite` + `npm run dev`; includes the axe accessibility scans).

**Uploading an update to the website (and the stale-page trap):** `npm run zip:lite` builds the tool and writes `cellar-planner/cellar-lite-upload.zip` (forward-slash paths, plus `lite-wordpress/cellar-lite.htaccess` as `.htaccess`). Extract it over the website's `cellar-lite` folder. **The folder must not share a name with a WordPress page slug** (the folder wins). The files in `assets/` have a fingerprint in their name, so an update is a new set of names and `index.html` is the only file that points at them: if a cache keeps serving an OLD `index.html`, the browser asks for the old names and gets 404s (seen on SiteGround: its nginx proxy cache answered `/cellar-lite/` with `X-Proxy-Cache: HIT` and the old page while `/cellar-lite/index.html` was already new, and static files were sent with `max-age=15552000`, six months). The bundled `.htaccess` sets `Cache-Control: no-cache` on `index.html` (long, immutable caching on the fingerprinted js/css). After uploading: flush SiteGround Site Tools -> Speed -> Caching -> Dynamic Cache, then hard-refresh; if an old page still shows, point the iframe at `.../cellar-lite/?v=2` (any new query string is a new cache entry). Check from outside with `curl -sI https://SITE/cellar-lite/` (look at `X-Proxy-Cache` and `Last-Modified`).

**Two ways to host it** (the bundle is plain files: no PHP, Node, database or server libraries are needed on either, only the ability to serve static files):
- **On Vault (Railway), recommended if SiteGround is awkward.** The root `npm run build` also builds the lite bundle into `dist/cellar-lite/` (`build:lite:vault`; non-fatal, so if it fails Vault still deploys), and Vault serves it at **`https://curam-vault.up.railway.app/cellar-lite/`**, with no login (`server/routes/cellarLiteRouter.js`, mounted in `server/index.js` before helmet and `requireAuth`; files only, no API, no database, no cookies). It gets its own headers: a strict Content-Security-Policy (own files only, no external calls), `no-cache` on the page and a year's caching on the hashed files, GET and HEAD only. **To let your website embed it, set `CELLAR_LITE_FRAME_ANCESTORS` on Railway** to your site's origin (for example `https://www.example.com.au`; several origins separated by spaces). Unset, only Vault itself can frame it, so the iframe on your site would be blocked. Invalid entries (wildcards, paths) are ignored with a warning. Then use the Railway address as the iframe `src` and as `PLANNER_ORIGIN` in `lite-wordpress/cellar-lite-fill.js`. Updating = push to `version-7` (Railway rebuilds). Tests: `npm run test:cellar-lite` (headers, the allow-list, caching, GET only, 404s, no login needed).
- **On SiteGround (or any static host):** upload the built folder, steps below.
Either way the embedding page is found from the browser's own ancestor-origin list (Chrome, Safari) or the referrer's origin (Firefox), never from the address, and the planner only posts to that origin.

**Build and update (static bundle, for SiteGround or any static host):**
1. `cd cellar-planner && npm run build:lite` writes `dist-lite/` (an `index.html` and `assets/`, relative paths, so any folder works; ignored by git). `npm run dev:lite` serves it on port 5177 (`/lite.html`).
2. Upload the contents of `dist-lite/` to the site, for example `public_html/cellar-lite/`, through Site Tools -> File Manager or SFTP. Replace the old `assets/` files; the new `index.html` points at the new ones.
3. On the WordPress page add a Custom HTML block with `<iframe src="https://YOUR-SITE/cellar-lite/" title="Wine cellar planner" style="width:100%;height:1100px;border:0"></iframe>` (same domain, so no header changes), and the script from `lite-wordpress/cellar-lite-fill.js` after checking its settings (`PLANNER_ORIGIN`, `FORM_SELECTOR`, `MESSAGE_FIELD`, `FIRST_FIELD`; the defaults match the wiwc.com.au contact form). It writes the design into the form's message box, so no extra fields are needed. The planner page and the contact page are different pages: enqueue the script on both. Do not name the folder the same as the WordPress page's slug (the folder would be served instead of the page).
4. Check the site's security plugin and any Content-Security-Policy allow the iframe and that script.

## Accessibility

Checked with **axe-core** (WCAG 2.1 A and AA) on the plan, the elevation and the guide: **0 violations**, as part of `npm run e2e`. What was done: grey, amber and error text and the orange buttons meet AA contrast (including on hover); the Plan/Elevation/wall buttons are toggle buttons (`aria-pressed`) in a labelled group; each drawing is a labelled image with a text description (size, door, runs, bottle total); every field has a visible label and a tooltip; the guide takes focus when it opens, closes on Esc, returns focus, and its scrolling text can be reached from the keyboard; there is a visible focus outline everywhere; the Test case and every other control work from the keyboard alone. Not covered by an automated scan: reading order with a real screen reader, and the drawings themselves for someone who cannot see them (the text description gives the headline numbers, not the layout).

## Staging checks (for you, by hand)

On staging: sign in, open **`/cellar-planner`**, and (admin) switch **Cellar Planner** on in **Settings → Feature Access** to see it in the nav. Or locally: `npm run dev` in `cellar-planner/`, open `http://127.0.0.1:5176/cellar-planner-app/`. Use a private window so nothing is "already seen".

1. The guide opens by itself; **Got it** closes it; refreshing does not reopen it; **(i)** does.
2. The compass starts the tour; step through all 13; **Finish** ends it; Esc ends it; `?tour=1` starts it. In Vault, **Settings → Cellar Planner Tour** (Take / Retake Tour) opens the page and runs it.
3. Hover every control in the left panel: each shows a short explanation, and none runs off the screen.
4. Load **Sample** and set it beside A101, A102 and A103. Report anything that differs: hinge side, door size, header, vents, the 940 | 970 | 940 split, the inside size.
5. Change the **Bottle** in the rack panel: Burgundy 960, Champagne 800; Magnum shows 0 with the 640 "not counted" and red runs. Switch orientation to **label-forward**: the total goes to "not set" and asks for its own bottles-per-row. A first visit already shows the Test case: 1,120 bottles, a banner and an "estimated" word on seven rack fields. Type over them: the markers go and the total follows. Then **Blank sample**: every rack value says "not set"; try **Fill the blanks with best guesses** and **Undo**. Or enter your own rack numbers and press **Fill** on the north wall; blank one field and the total goes back to "not set".
6. Set the door to swing in, set a minimum walkway, and place a run in front of it: the keep-clear zone and the warning appear.
7. Elevation: check each wall, and that the door diagonal points to the handle side. **Racks:** step through North, East, South, West: every bottle is drawn, the count on screen matches the total (north 560, south 280 in the Test case), the door's gap on the south wall, and Magnum turns them red.
8. **Saved designs:** rename the design, wait for **Saved**, reload: it is there. Open **Your designs**, make a New design, switch back. In a second tab change the same design and see **Save paused** with Keep mine / Use the saved one. Signed in, check the row in the account (`cellar_projects`) and that signed out it says "this browser". **Download file**, change something, **Upload file**: it comes back exactly (as a new design). **Drawing package:** fill in the form and download the PDF; open it beside A101 to A103. Check the title block, the scale, the dimensions, that the Test case's PDF says "BEST GUESSES ... NOT FOR QUOTING" on every sheet, and that the bottle count on the rack sheets matches the screen.
9. Anything the guide or a tooltip says that is wrong or confusing for a real customer or installer.

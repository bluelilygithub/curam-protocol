# Cellar Planner

Walk-in wine cellar configurator. **Glass enclosure with metal racking first**, then carcass joinery. Bespoke-first: everything is driven by dimensions in whole millimetres, not product codes. Code: `vault/cellar-planner/` (own Vite app on `planner-core`). Full specification and decisions log: `cellar-planner/specs/spec-v1.md` (v1.1).

> **Status: in Vault, switched off by default.** The page is at **`/cellar-planner`** (an iframe hosting the built app at `/cellar-planner-app/`, the same pattern as Garden Planner), with a nav item **Cellar Planner** (Content Creation), a Settings â†’ **Cellar Planner Tour** card, and the feature flag **`cellarPlanner`**. The flag **defaults to off** (it is a work in progress with unverified values): an admin switches it on in **Settings â†’ Feature Access**, which shows the nav item. The `/cellar-planner` page itself does not depend on the flag (as for the other planners), so the address works for any signed-in user. Designs save to the Vault account through `/api/cellar-projects` (table `cellar_projects`, behind `requireFeature('cellarPlanner')`), with a `.cellar.json` file download and a browser draft as fallbacks. It is built by the root `npm run build` (`scripts/buildCellarPlanner.js`, non-fatal: if it fails Vault still deploys and the page shows a "not available in this build" notice). It can also run alone with `npm run dev` inside `cellar-planner/` (port 5176, `http://127.0.0.1:5176/cellar-planner-app/`, trailing slash included).

## Using it

- **The first visit opens the Test case**, so there is never an empty screen. After that the saved draft comes back (so a browser that already has a blank draft keeps it until you press **Test case**). **Test case** (button, `?testcase=1`, or open `examples/test-case-1.cellar.json`) loads the sample enclosure with racks on every wall (4 units north, 1 either side of the door on the south, 1 each on east and west) filled with **best-guess rack values**: a 600 x 350 mm unit, 2000 mm tall, 100 mm row pitch, 7 neck-out bottles a row, 2 posts, **1,120 bottles**. **These are invented, not a supplier's.** Each is marked **estimated** (a visible word, not just colour) with a banner saying not to quote from them; typing your own number over one, even the same number, removes its marker, and undo brings it back. The minimum walkway stays blank. `npm run example` rewrites the example file from the app's own test case, and a test fails if they differ.
- **Blank sample** (the old "Sample" button) loads the Carter Noir sample enclosure **as read**, with the racks left blank, and the amber "not set" banner has a **Fill the blanks with best guesses** button that fills only the blank rack fields (keeping anything you typed, marking just those estimated; Undo takes them back). The sample is the Carter Noir enclosure **as read** from sheets A101 to A103 (2850 x 1665 x 2200 mm, 50 mm panels, a 970 x 2120 door centred on the south wall hinged on the left, a 500 mm header with a conditioner and two vents). **Every number from the sample is unverified.**
- **Enclosure panel:** outer sizes (to the outer faces), ceiling and floor build-up, header height. **Walls:** each wall's kind (insulated panel, framed glass, stud wall) and build-up; the build-ups are taken off to give the **inside size** (sample: 2750 x 1565 x 2150). **Door:** wall, size, swing, hinge as seen from outside, offset (blank = centred), glazed. **Header:** conditioner and vents, positioned from the header's left end.
- **Rack specification:** unit width, depth, height; row pitch; bottles per row; orientation; posts; optional rows. **All start blank.** **Minimum walkway:** blank until you set it.
- **Rack runs:** add a run on a wall, or **Fill** a wall with whole units (leaving the door opening free).
- **Plan** (from above), **Elevation** (any wall, seen from outside) and **Racks** (the inside face of any wall, seen from inside, with **every bottle drawn at its true size and spacing**: end-on circles for neck-out racks, side-on rectangles for label-forward; rows are one row pitch apart standing on the floor; the door's opening is shown on its wall; units still missing values are an outline only, never filled with guessed bottles; runs with an error are red and say "not counted", matching the total). Scroll to zoom, drag to pan, **Fit**.
- **Drawing package** (button): fill in the title block (company, client, address, project number, drawn by, checked by, date) and **Download PDF**: A3 landscape sheets, **A100** specification and schedule, **A101** plan, **A102** door-wall elevation, **A103 onward** the racks on each wall with every bottle at true size, each with the title block and the red "preliminary design only" line, and a status line saying whether the rack values are best guesses, not set or entered. The details are kept with the design. A design with no racks makes three sheets; once racks are placed it also gets a **3D VIEW** sheet (the 3D picture of the inside).
- **Checks** (errors, then warnings, then information, each with a plain fix, and a one-click fix button where one really helps) and **Advisory guidance** are on the right. Drag a run on the plan to move it; the strip above the drawing always shows bottles, units, price and errors.
- **Rack type**, **Price**, **Cooling**, the **3D** tab, **Enquiries**, **Quote** and the calculator help button are described in the sections below ("Shared rack catalogue", "Enquiries", "Technician workflow", "Cooling estimate and the 3D view", "Help for technicians").
- **Saved designs** (`src/app/designs.ts`, `designLibrary.ts`, `ui/JobsPage.tsx` (the Jobs page), `ui/DesignsPanel.tsx` (save status, conflict bar)): jobs (saved designs) save by themselves, 1.5 s after the last change, to **the Vault account** (table `cellar_projects`, `/api/cellar-projects`, behind the `cellarPlanner` flag) when the planner is opened from Vault while signed in, otherwise to **this browser** (and the header says which: "Saved to your Vault account âœ“" or "Saved on this device only âœ“"; **Save now** saves at once). It is the same library machinery as Room and Garden Planner (`planner-core/library`: `ProjectsController`, optimistic `expectedUpdatedAt` save, a 409 pauses saving and the header offers **Keep mine / Use the saved one**, unsaved changes from a closed tab are restored, and an unreachable Vault falls back to the browser with a note). **Jobs** lists them (name, rack runs, units, "best-guess values", saved time) with New design, Open file, Copy and Delete (inline Yes / No). The first design of a new library is the Test case; New design is the blank sample. **Test case, Blank sample and Open file ADD a design and open it; they never overwrite the open one.** A draft an older version kept in the browser becomes the first saved design (and is carried to an empty account once). Limits: 200 designs per user, 2 MB each. The browser draft is still kept on every change. **Download file / Upload file** (a `.cellar.json`) still move a design in and out as a file. Undo and redo cover every edit except typing the name (no undo step, so it saves quietly).

### The rules that matter

- **The total only counts runs that can be built (D-18).** A run with an error (too tall for the inside, too shallow for the bottle, off the end of its wall, in the door's way, a bottle that cannot fit) is left out of the headline number; the panel says "Not counted: n bottles in m runs with errors" and the plan labels that run "not counted (has an error)". Warnings and notes do not remove a run. Example: Test case, Magnum bottle: headline 0, 640 bottles not counted in 5 runs.
- **Bottles per row is calculated unless typed (D-19).** Blank, it is the unit width divided by the bottle's slot pitch (600 mm: Bordeaux 7, Burgundy 6, Champagne 5, Magnum 4), shown as "calculated" with a note that it is an estimate; a typed number is the fabricator's and wins. So the **Bottle** setting moves the count. A typed number that cannot fit across the unit (9 Bordeaux need 684 mm; a 600 mm unit holds 7) is `RACK_ROW_TOO_WIDE`. The Test case leaves it calculated.
- **Label-forward has its own bottles-per-row (D-20),** never calculated and "not set" until typed: the neck-out figure never carries over, because on a metal rack label-forward may mean the bottle lies side-on and takes about its own length of width.
- **Blank is "not set", never zero.** A blank rack field is shown as "not set"; a run with a blank unit width or depth has no footprint and is skipped by the geometry; the bottle total reads "not set (n runs without rack values)" until every run is complete; `RACK_SPEC_MISSING` names the missing values. There are no invented rack defaults.
- **The walkway minimum has no default and is only ever a warning.** Blank = not checked (one information note says so). A step-in glass cabinet and a walk-in room are designed to different minimums (D-17).
- **The floor-inside-the-door check applies only when the door swings in.** An inward door also gets the swing sweep tested as a true quarter circle.
- **Advisory guidance never blocks a design.** Insulation, glass (about 1.4 W/m2K or better, thermal breaks, sealed doors) and heat-source notes from the Kings Winehaus guide are information only and always begin *"Advisory only: requires mechanical engineer / HVAC sign-off."* The glass share (and the advisory 50% note that uses it) is measured on the **outer faces** (10.35% for the sample).
- **Every drawing carries** `PRELIMINARY DESIGN ONLY: FINAL SITE MEASURE REQUIRED PRIOR TO FABRICATION`.
- **The header is a bulkhead above the enclosure**, not space inside it, so it never reduces the inside height.
- **Label-forward depth is a joinery assumption on metal racks** (inclined footprint plus a 20 mm lip) until the fabricator confirms how their rods hold the bottle.

## Help: guide, tour, tooltips

Same pattern as Room Planner and Garden Planner.

- **How this works** (`src/ui/InfoModal.tsx`, the **(i)** button): the plain-language guide. **Opens once on the first visit** (localStorage `cellar-planner:info-seen:v1`), then from the button. It is kept in step with the features: when one changes, update the guide, the tour and the tooltips together.
- **Guided tour** (`src/help/cellarTour.ts`, the **compass** button): 17 Shepherd.js steps (including Price, Cooling, 3D, Enquiries and Quote) (the same library and look as Vault's tours), loaded on first use so it stays out of the main bundle. The tour is data (`TOUR_STEPS`), tested against the `data-tour` hooks on the screen so it cannot drift away from it. The elevation step switches to the elevation and the drawing step back to the plan; the screen is put back when the tour ends. Completing or skipping sets **`vault_tour_cellar_planner_completed`** (the key Vault's other tours use, so Settings can show "Retake Tour"), and **`?tour=1`** starts it (how Vault's Settings page will retake it).
- **Tooltips:** the shared themed tooltip (`@planner-core/help/TooltipHost`, the same look as Vault's). Every button, field, menu and tab has a plain-language `title` or `hint`, written as real sentences; a test fails if one is missing. Cards are capped at 160 px wide: the shared placement keeps a card's centre 80 px from the window edge, so a wider card runs off the screen beside the left panel. (This is a latent limit in `planner-core/src/help/tooltipLogic.ts`, which assumes 240 px cards; it was not changed here because it is shared with the other planners.)

## The Racks view: the count in words, and how accurate the picture is

The Racks view (and lite's "Racks on a wall") lists the wall's bottles in a sentence under the drawing, for example "North wall: 560 bottles in 4 units (140 a unit: 20 rows of 7)." (`rackWallSummary()` in `src/views/rackView.ts`). It says "no racks" for an empty wall, names units with an error as **not counted** (with their bottles) and units with values missing as having **no bottles counted**.

**What the picture does and does not show.** One circle (or side-on rectangle for label-forward) is drawn for every bottle the count includes, no more and no fewer: a test checks that the circles on every wall equal the words and add up to the total, for the Test case and for every bottle style, door wall and door type the lite tool can make. Bottle circles are the bottle's true diameter. What is **modelled, not measured**: bottles are spread evenly across each unit's width (the real pin spacing is the fabricator's), rows are one row pitch apart from the floor (the first row's offset is not modelled), and each circle is one bottle lying front to back, one deep (racks that hold bottles two deep, or double-sided racks, are not modelled and would hold more). Rack sizes are best guesses until the fabricator supplies real ones, so the count is an estimate even though the picture matches it exactly.

## Single and double doors

Added 2026-10-09. `DoorSpec.leaves` is `1` (a single leaf, also when absent, so every earlier file and design opens unchanged) or `2`.

- **Double door:** two equal leaves that together fill `widthMm` (the whole opening), each hinged at an outer edge and meeting in the middle. The `hinge` setting is not used for a double door (the panel hides it). Each leaf sweeps a quarter circle of **half the opening** (`doorLeafWidthMm`), so a 1500 mm double door sweeps two 750 mm arcs, not one 1500 mm arc.
- **Where it shows:** the Door panel's **Door type** (switching to double sets the opening to at least 1500 mm, back to single to at most 970 mm; one undo step), the plan (an arc per leaf, `doorLeaves()` in `placement.ts`), the elevation (labelled DOUBLE DOOR, a diagonal on each leaf and the meeting line), the inward-swing and keep-clear checks (a rack is flagged if it meets either leaf's arc), the drawing package's door row, and the guide and tour text.
- **Check:** `DOUBLE_DOOR_TOO_NARROW` (error) when the opening is under 800 mm (leaves under 400 mm). `DOOR_TOO_WIDE` applies to the whole opening.
- **Not modelled yet:** a double door with one fixed leaf (only one opening), and different leaf widths. The 1500 mm default is a typical figure to confirm, like the 970 mm single door.
- **Lite tool:** a **Door type** question (single, about 970 mm, or double, about 1500 mm), in the design code as an eighth value (codes with seven values, made before this, open as single doors), in the enquiry summary line, the guide and the tour. The opening shrinks to fit a short door wall (an even number of mm for a double door).
- **Tests:** `tests/doubledoor.test.ts` (geometry, checks, drawings, saving), `tests/lite.test.ts`, and the door checks in `scripts/e2e.mjs` and `scripts/e2e-lite.mjs`.

## Lite version for the public website

Started 2026-10-09. A "play" tool for visitors: a static bundle (no Vault login, no API calls, nothing stored) embedded by iframe in the WordPress site on SiteGround. Every figure says **estimate only, not a quote**.

**What the visitor does:** types the inside width, depth and height, picks the door wall and the main bottle style, and chooses "as many as fit" or "a number I choose". They see a bottle estimate, a plan from above and the racks on any wall (pinch-zoom works), and can press **Request a quote**, which hands their design to the site's enquiry form.

**Standard rack units:** every lite estimate is built from one standard-size rack unit (`LITE_UNIT_WIDTH_MM`, 600 mm wide, a typical size not a confirmed supplier value), placed whole, so leftover space at the end of a wall shows as a gap. This is stated on the screen under the drawing, in the guide ("Standard rack units"), in the tour's estimate and drawings steps, and in the enquiry summary line. Keep those in step if the unit size changes.

**Code** (`cellar-planner/`):
- `src/lite/settings.ts` is the pure core: `LiteSettings` (clamped to `LIMITS`), `liteToProject()` (the Carter Noir sample resized to the inside size, best-guess racks marked estimated, north and south own the corners, east and west fit between; deep enough for the chosen bottle, so a magnum gets a deeper unit), `trimToTarget()` (removes whole units, east then west then south then north, never adds), `liteResult()` (estimate, the room's maximum, plain problems) and the **design code**.
- `src/lite/LiteApp.tsx` + `lite.css` is the screen; `lite.html` is its page, `vite.lite.config.ts` its build.
- `lite-wordpress/cellar-lite-fill.js` is the small script for the WordPress page.
- Reused as they are: `src/enclosure`, `src/rack`, `src/placement`, `src/views`, `src/ui/DrawingView.tsx`.

**Help for a casual visitor** (written in plain words, no planning jargon):
- **Guide** (`src/lite/LiteHelp.tsx`, the **Help** button): what the tool is, each question in plain words (how to measure the inside, what South/North/East/West mean on the drawing, what the four bottle styles are), what the two drawings show, what asking for a quote does and sends, and that figures are estimates. **Opens only from the Help button** (it used to pop up on a first visit; most visitors closed it unread, so a three-step strip on the page replaced that); Esc closes it.
- **Tour** (`src/lite/liteTour.ts`, the **Take the tour** button, or `?tour=1` on the address): ten Shepherd steps in the order the screen asks things: size, door, bottle, how many, the estimate, the drawings, the quote button. Loaded on first use so it stays out of the first download. Finishing sets `cellar-lite:tour-done:v1`.
- **Always-visible hints:** a one-line explanation sits under every question (no hover needed, unlike the full planner). All wording is in those three files, plus the field labels in `LiteApp.tsx`, for the owner's wording review.

**Design code:** `CL1.` plus base64url of `[width, depth, height, doorWall, bottle, mode, target]`. Settings only, no personal data. A link `lite.html?d=CL1....` reopens the design; the address is kept up to date as the visitor edits. Unreadable, newer-version or out-of-range codes are refused or clamped, never trusted.

**Hand-off to the enquiry form:** the embedded page posts `{ type: 'cellar-lite:design', version: 1, code, summary, bottles, requested }` to the page around it, addressed to the origin of `document.referrer` (never broadcast; nothing is posted when not embedded). The WordPress script accepts a message only from the planner's own origin, checks the code's shape and the summary length, and, once when **Request a quote** is pressed, takes the visitor to the contact page (`CONTACT_URL`) with the design in the address (`?cellar-design=` and `?cellar-summary=`). The same script on the contact page writes the summary, code and a "View this design again" link (`PLANNER_LINK` + `?d=<code>`, which reopens the design in the standalone planner) into the form's message box as one marked block, scrolls to the form, focuses its first field and removes the design from the address. The script must be loaded on BOTH pages; it logs each step to the Console while `DEBUG` is true. The revealed panel is always scrolled into view in the planner, and is the fallback (**Copy my design**) if nothing happens. The visitor still presses the form's own Send. Without the script, the quote step shows the summary and code with a **Copy my design** button to paste into the form. **No server of ours is involved**: the enquiry goes through the site's own form and email.

**Staff side (full planner):** **From design code** (title bar, Examples group) takes a pasted code, a "Design code: ..." line or a whole enquiry email, and **adds** the design as a new one (never overwrites). `?d=CL1....` on the full planner's address does the same on load. The result is the same enclosure, runs and bottle total the visitor saw (a unit test covers lite settings -> code -> project -> saved file -> reopened).

**Settings the owner controls (Vault: the Cellar Planner page, **Settings** button beside **Planner** at the top, admins only (the button is not shown to anyone else and `/api/admin/cellar-lite/config` needs `requireAdmin`); ten collapsible cards in three groups (Products and prices / Public website planner / Staff planner and quote), each header showing a one-line summary of what is set, open/closed remembered in the browser, Open all / Close all, and a Save bar that stays at the bottom; it used to be a tab in Vault's Settings):** the rack types (see **Shared rack catalogue** below; the public tool uses the default one's width and height), single and double door widths, a guide-price formula, the line under the heading, and the starting rooms. Stored as one JSON value in `workspace_settings` (key `cellar_lite_config`); the rules for a valid value are in `server/config/cellarLiteConfig.js` (the admin screen shows the plain-language reason when a value is refused). The public tool is static files on the business's website, so it **fetches** them when it opens from `GET /api/cellar-lite/config` (no login, read-only, `Access-Control-Allow-Origin: *`, cached 30 s server side and 60 s in the browser; Vault must be deployed for this to work). If that request fails for any reason the tool uses the last settings it remembered in that browser, else its built-in defaults (`src/lite/config.ts`, kept equal to the server's by a test), and the browser Console says which and why (`[cellar-lite] ...`). Prices are only sent while "Showing to visitors" is on, so unpublished amounts never leave Vault. Guide price = fixed + per rack unit x number of whole units + the door price, shown as a range (+/- %) rounded to the chosen step; nothing is shown unless at least one amount is entered. A rack unit is never taller than the room. Starting rooms replace only the size and door style. **Copy a link to this design** copies the standalone planner's address with `?d=<code>`. Beside it, **How is this price worked out?** (only while a guide price is showing) opens a modal (`src/lite/PriceHelp.tsx`) that outlines how the price follows from the visitor's own choices: it names the parts in use (racking, door, the basics every cellar needs; a part is mentioned only if the owner set an amount for it) and shows how many rack units and which door THIS design has, but never any amount. Every control in the planner carries a `title` and the shared `TooltipHost` shows it as the themed tooltip; every field and button on the admin tab uses Vault's `Tooltip`. Tests: `npm run test:cellar-lite-config` (server), `npm test` in `cellar-planner/` (`tests/liteConfig.test.ts`, incl. the browser/server agreement check).

**Shared rack catalogue and staff price (Cellar Planner -> Settings -> Rack types).** The owner keeps a **catalogue of rack types** (up to 8: name, unit width/height/depth, row pitch, orientation, posts, bottles per row, bottles per row label-forward, rows per unit, **price per unit**, and a **Confirmed by supplier** tick), one marked the **default**. Blank = "not set", never zero. It is the single source for both tools: the public lite tool reads the default type (served as `rack` and `pricing.perUnit`, the same shape as before, so pages with an older copy keep working; settings saved before types existed become one "Standard rack"), and the **staff Cellar Planner** reads the whole catalogue plus the real prices from the signed-in `GET /api/cellar-planner/catalogue` (behind `requireAuth` + `requireFeature('cellarPlanner')`, `Cache-Control: no-store`; `staffView()` in `server/config/cellarLiteConfig.js`). While the public price is hidden, `publicView()` blanks every type's price too. Staff side (`cellar-planner/src/app/catalogue.ts`): the **Rack type** picker in Rack specification copies a type's numbers into the design (the design stays self-contained, so a later catalogue change never alters it; if the values then differ from the catalogue a note offers "Use the catalogue's values again"); a **confirmed** type marks nothing estimated, an **unconfirmed** one marks every value it has estimated (blanks stay "not set") and the drawing package says "NOT YET CONFIRMED BY THE SUPPLIER". New blank designs start with the default type. The **Price** panel is the full breakdown (fixed amount + units x the type's price + single/double door price, and the range a customer would see); it shows even when the public price is off, warns for unconfirmed types, a type with no price or a design with errors, and says why when there is no price (no catalogue, no type chosen, type removed, no racks, no amounts). The catalogue is remembered in the browser for offline use; without a Vault sign-in the planner still works, with a note instead of the picker. Tests: `node server/routes/cellarLiteConfig.test.js` (rules, legacy migration, public vs staff views), `tests/catalogue.test.ts` + `tests/liteConfig.test.ts` (browser and server rules must agree), `npm run e2e:catalogue` inside `cellar-planner/` (real Chrome, Vault's endpoints stood in for at the network layer, incl. accessibility scans).

**Feature options ("Make it yours") and their prices.** *What it is.* The owner keeps a list of finishing touches in **Cellar Planner -> Settings -> Feature options**: up to ten **groups** (front and doors, lighting, special storage, centrepiece, climate, wall finish, flooring are the starting list) of up to eight **options** each. A group is **pick one** (exactly one option is the standard, marked **Included**, costing nothing extra; choosing another swaps it) or **pick any** (no standard; add as many as wanted). Each option has a name, a one-line description, an optional badge (Popular / Recommended), a **low** and a **high** price (blank = not set, shown as "price on request", never counted as zero), optional smallest room width/depth (the option is greyed out with the reason when the room is smaller; the starting "Island with drawers" needs 2.4 m depth), an **Available** switch, and what it changes in the 3D picture: **timber doors**, **glass doors**, **full glass front** (drawn at the real door position on the door wall: one leaf, or two with a mullion for a double door; timber is see-through so the cellar stays visible), **ceiling downlights** (glowing spots and their pools of light), **LED strips** along every rack row, **backlit racks**, a **tasting bench** or **island** on the floor (illustrative position), **timber or stone walls**, **stone or oak floor**; everything else is text and price only. **Cooling estimate and the 3D view (staff planner).** *Cooling* (`enclosure/cooling.ts`, **Cooling** panel, section "Cooling needed" in the technician help): an INDICATIVE load, the standard steady-state method. Heat through each surface = U x area x temperature difference, with areas to the outer faces; U of an insulated wall, ceiling or floor = insulation conductivity / thickness (m); glass and glazed doors use the glass U-value; the door takes its own area out of its wall (opaque, it is insulated like its wall); a floor with no build-up is a bare slab (its own U-value, with a note); a wall or the ceiling with no thickness gives "not set", never a guess; a target at or above the outside temperature says why there is no estimate. Then + lights/people/stock (W) + a safety margin (%). The assumptions are the owner's in **Cellar Planner -> Settings -> Cooling estimate assumptions** (conductivity 0.025 W/m.K, glass 1.4, bare floor 1.0, gains 100 W, margin 20%, target 14 C, outside 35 C: typical starting values, to be confirmed with the supplier/HVAC person); the two temperatures can be overridden per design (`project.cooling`). Each conditioner in the header has an optional **Cooling capacity (W)**; the panel then says the header covers the load (with the spare) or is N W short, "not rated" until every conditioner has a capacity (never counted as zero). Always labelled a guide for choosing a conditioner; HVAC sign-off is still needed. A bigger cellar needs more (surface area grows), thicker insulation less. *3D view:* a **3D** tab beside Plan/Elevation/Racks reuses the public tool's inside-the-cellar scene (`lite/cellarScene.ts`, `lite/CellarView.tsx`; drag to look, zoom buttons, inside measurements) fed by the staff design, with an Oak/Walnut/Black finish kept with the design (`project.finish`, colour only, never a count). Racks against the door wall are seen from behind (the near wall is cut away), so their bottles are not drawn; the tab says so. The same picture (`export/insidePicture.ts`, 1200 x 760 JPEG) goes into the **drawing package as an extra "3D VIEW" sheet** and onto the **customer quote** beside the cellar details; if it cannot be drawn the PDFs are made without it. **Uploading an update to the website (and the stale-page trap):** `npm run zip:lite` builds the tool and writes `cellar-planner/cellar-lite-upload.zip` (forward-slash paths, plus `lite-wordpress/cellar-lite.htaccess` as `.htaccess`). Extract it over the website's `cellar-lite` folder. **The folder must not share a name with a WordPress page slug** (the folder wins). The files in `assets/` have a fingerprint in their name, so an update is a new set of names and `index.html` is the only file that points at them: if a cache keeps serving an OLD `index.html`, the browser asks for the old names and gets 404s (seen on SiteGround: its nginx proxy cache answered `/cellar-lite/` with `X-Proxy-Cache: HIT` and the old page while `/cellar-lite/index.html` was already new, and static files were sent with `max-age=15552000`, six months). The bundled `.htaccess` sets `Cache-Control: no-cache` on `index.html` (long, immutable caching on the fingerprinted js/css). After uploading: flush SiteGround Site Tools -> Speed -> Caching -> Dynamic Cache, then hard-refresh; if an old page still shows, point the iframe at `.../cellar-lite/?v=2` (any new query string is a new cache entry). Check from outside with `curl -sI https://SITE/cellar-lite/` (look at `X-Proxy-Cache` and `Last-Modified`).

**Two ways to host it** (the bundle is plain files: no PHP, Node, database or server libraries are needed on either, only the ability to serve static files):
- **On Vault (Railway), recommended if SiteGround is awkward.** The root `npm run build` also builds the lite bundle into `dist/cellar-lite/` (`build:lite:vault`; non-fatal, so if it fails Vault still deploys), and Vault serves it at **`https://curam-vault.up.railway.app/cellar-lite/`**, with no login (`server/routes/cellarLiteRouter.js`, mounted in `server/index.js` before helmet and `requireAuth`; files only, no API, no database, no cookies). It gets its own headers: a strict Content-Security-Policy (own files only, no external calls), `no-cache` on the page and a year's caching on the hashed files, GET and HEAD only. **To let your website embed it, set `CELLAR_LITE_FRAME_ANCESTORS` on Railway** to your site's origin (for example `https://www.example.com.au`; several origins separated by spaces). Unset, only Vault itself can frame it, so the iframe on your site would be blocked. Invalid entries (wildcards, paths) are ignored with a warning. Then use the Railway address as the iframe `src` and as `PLANNER_ORIGIN` in `lite-wordpress/cellar-lite-fill.js`. Updating = push to `version-7` (Railway rebuilds). Tests: `npm run test:cellar-lite` (headers, the allow-list, caching, GET only, 404s, no login needed).
- **On SiteGround (or any static host):** upload the built folder, steps below.
Either way the embedding page is found from the browser's own ancestor-origin list (Chrome, Safari) or the referrer's origin (Firefox), never from the address, and the planner only posts to that origin.

**Build and update (static bundle, for SiteGround or any static host):**

On the WordPress page add a Custom HTML block with `<iframe src="https://YOUR-SITE/cellar-lite/" title="Wine cellar planner" style="width:100%;height:1100px;border:0"></iframe>` (same domain, so no header changes), and the script from `lite-wordpress/cellar-lite-fill.js` after checking its settings (`PLANNER_ORIGIN`, `FORM_SELECTOR`, `MESSAGE_FIELD`, `FIRST_FIELD`; the defaults match the wiwc.com.au contact form). **Pop-ups and the tour inside the website frame.** The frame is as tall as the planner, so a pop-up centred in it landed in the middle of the page, not the screen. The page script already sends where the visible window is (`cellar-lite:viewport`); `LiteApp.tsx` turns it into `--vis-top` / `--vis-h`, and `lite.css` (`html[data-embedded]`) places `.modal-back` (Help, price help) and the tour's centred cards inside that window. `node scripts/e2e-lite-guide.mjs` checks both on a scrolled page. Needs `STICKY_PICTURE` left on in the page script (its default). The page script also reports `topInset` (`TOP_INSET`, -1 = find a fixed or sticky site menu by itself), so pop-ups sit below the site menu, and the pop-up is limited to the visible height (`.modal` used 100vh, the whole frame, which pushed its top off screen).

**Render photo and Save picture (public tool).** Under the 3D picture, desktop and tablet only (a phone sees "Render photo is not available on a phone" and no button; the width is the same 700 px the phone notice uses). Render photo makes a realistic path-traced picture of the visitor's design **in their own browser** (no server, no AI, nothing sent anywhere), so it matches the design exactly and costs nothing to run. Pieces: `src/lite/photoGeometry.ts` (pure: the design as real shapes, the same racks and bottles the on-screen picture draws, plus the camera for **From the doorway** or **From above**; `MAX_PHOTO_BOTTLES` caps a huge design), `src/lite/photoTracer.ts` (the three.js scene and `three-gpu-pathtracer`; lazy-loaded, about 740 KB, only fetched when the button is pressed), `src/lite/PhotoModal.tsx` (the window), and the shared job/estimate code in `planner-core/render3d/photo.ts`. **Render-time awareness:** the window says before anything starts that it takes time (Quick look about 1 to 3 minutes, Good about 5 to 15, longer on a tablet), to keep the page open and on screen, and shows a progress bar with a time estimate once it has measured the device's speed; it can be paused or stopped and a stopped picture can still be saved. Sizes are 640x360, 1280x720 and 1920x1080 (no 4K) and qualities Quick look and Good (no Best). **Fair use:** 3 pictures per visit (`RENDERS_PER_VISIT`, counted in `sessionStorage`), one at a time; it only protects the visitor's device. The saved PNG has a caption strip with the design name, "Preliminary design only" and the date. **Save picture** saves the on-screen 3D picture instantly (same caption). A device without WebGL2 float support is told so. Tests: `tests/photoGeometry.test.ts` and `node scripts/e2e-lite-photo.mjs` (real Chrome with software graphics, so it asks for only a few passes through `window.__cellarPhotoSamples`, which can lower the pass count but never raise it; `PHOTO_SAMPLES=24` for a closer look, screenshots to the folder given as the argument). Not built: lighting choices, the door leaves seen from inside, glass reflections of an outside, and a 4K size.

**Other costs and margin (staff only).** The price used to cover only racks, the door and feature options. It now also carries **glass walls** (the glass wall area in square metres x a price per m2; the door has its own line), a **cooling unit**, **lighting**, **installation** (one amount per job each) and a **margin** (a per cent on top of everything). They live in **Cellar Planner -> Settings -> Other costs and margin** (`costs` in `server/config/cellarLiteConfig.js`, mirrored in `cellar-planner/src/lite/config.ts`; staff only: `publicView` strips them and only `/api/cellar-planner/catalogue` carries them). **Every amount starts as a PLACEHOLDER** (`confirmed: false`): rough figures from public cost guides (glass walls about 1,400 per m2, cooling unit 6,500, lighting 1,200, installation 3,500, margin 25%), mostly US and Canadian and **not supplier quotes and not checked for Australia**. The Price panel marks each one "placeholder" and warns, the "How the numbers are calculated" help explains them, and **a customer quote is refused while any is a placeholder or blank** (`quoteBlockers`), so a guess never reaches a customer. The owner ticks **Confirmed** per line when it is a real figure. A blank amount is "not set" (left out, never zero, and it also blocks the quote); a confirmed 0 means no charge and shows no line. On the **customer's quote the margin is never a line**: `customerLines` folds it into the other lines in proportion so they add up to the same total (and drops their per-line working, which would no longer match). The customer range (from the guide price) includes the cost lines and the margin. Tests: `tests/costs.test.ts`, `server/routes/cellarLiteConfig.test.js`, `node scripts/e2e-costs.mjs`.

**DXF export (CAD handover).** **Cellar Planner -> Drawing package -> Download DXF** gives the plan, the door-wall elevation and each wall of racks as a CAD file (`src/export/dxf.ts`, `makeDxf`): ASCII DXF **release 12 (AC1009)**, the oldest and most widely read, with plain LINE / POLYLINE / CIRCLE / TEXT entities only, **millimetres at full size (1:1)**, one layer per kind of thing (`CELLAR-WALL-PANEL`, `CELLAR-GLASS`, `CELLAR-RACK`, `CELLAR-BOTTLE`, `CELLAR-DIMENSION` ...), the views side by side with a title above each, the preliminary statement and the title block details at the top left, a circle for every bottle (the test case has 1,120). It uses the **same drawing primitives as the PDF package** (`views/`), so the two cannot disagree. Opens in AutoCAD, BricsCAD, LibreCAD, DraftSight and similar, and can be linked into Revit. Not IFC, no DIMENSION entities, no 3D. Checked by reading the file back with the independent `ezdxf` library (0 audit errors, the right entity counts, outer size 2,850 x 2,200 mm for the sample); it has not been opened in AutoCAD itself. Tests: `tests/dxf.test.ts` (`DXF_OUT=file.dxf` writes one for an outside check), `node scripts/e2e-costs.mjs`.

**Request a quote now asks for the details inside the public planner (changed 2026-10-19).** The visitor is no longer sent to the contact page. **Request a quote** (Review step, the bottom bar, and the phone bar on the page) opens a short form in the planner (`src/lite/QuoteForm.tsx`): name, email, phone (optional), **state or territory** (the eight Australian ones) and an optional message, with the owner's reassurance line (Settings quote note) and the design summary. Nothing is sent until **Send my enquiry**. It posts straight to Vault's public `POST /api/cellar-lite/enquiry` (text/plain, no login; `credentials: omit`), which validates it again (state must be one of the eight; a hidden `website` box is the spam trap), files it in the CRM as before (client, contact, lead deal; the state is in the deal note and in `cellar_leads.state`, shown on the enquiries list data), and **emails every admin address** with the details, a link that opens the design in the staff planner, and Reply-To the visitor (`notifyOwner` in `cellarLeadsRouter.js`, sent after the answer, never fails or delays it; needs the email provider set up, otherwise only the CRM and Enquiries list know). The page script's phone bar now asks the planner to open its own form (`cellar-lite:go` with id `quote`); the planner no longer reports `requested`, so the old go-to-contact redirect never fires (an older page script falls back to it only if it cannot reach the frame). The contact page's fill-from-address and the copy-to-Vault on the site's own form still work for old links.
